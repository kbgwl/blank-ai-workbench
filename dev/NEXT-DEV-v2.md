## 一、背景与依据

T-R2-01「写类工具只回执」已验收通过（`edit_file`/`write_file` 去掉全文 diff，改计数回执），
但实测确认：**模型上下文里的写工具 diff 早已被 `payload.py` 的 `DROP_DIFF_TOOLS` 丢弃**，
本步只减小了 `tool.completed` 事件与检查点体积，**模型上下文的 token 峰值并未下降**。

当前最大短板仍是 token（用户目标：质量 ∧ 速度 ∧ 省 token 三者同时成立）：

| 指标 | kbgai | Claude Code | 差距 |
|---|---|---|---|
| 质量（隐藏验收） | 96.5 | 97.5 | -1.0 |
| 平均 token | 225K | 128K | 1.76 倍 |
| 速度 | 25s | 持平 | 0 |

T09 类任务基线：**19 次调用 / 487,764 prompt token / active context 25,517**。
调用次数是 token 主因——每轮调用都把历史完整重发一遍。

**结论**：下一版做降 token 第二波，两个杠杆一起上：文件状态快照（减每轮发送量）+
压调用次数（减轮次）。

## 二、目标与验收判据

**目标**：同批任务上下文峰值降 ≥ 30%，历史膨胀率降 ≥ 50%，调用次数显著下降，
不牺牲隐藏验收通过率。

**机器可执行判据**（沿用路线图 v2）：

| 维度 | 判据 |
|---|---|
| token | 上下文峰值下降 ≥ 30%；历史膨胀率下降 ≥ 50%；同批任务平均 token ≤ 对标产品 |
| 质量 | 隐藏验收通过率 100%；零改动伪成功拦截 100%；不出现回归 |
| 速度 | 单轮耗时不升；同批任务平均耗时不升 |

**验证方式**：每项改完用 `evals/compare.mjs` 同批任务对照，出改前改后
token / 调用数 / 步数 / 通过率，不以交付文本自述为准。

## 三、任务一：文件状态快照取代历史回放

### 现状
- 上下文单调增长：模型读过/写过的文件内容在历史里反复重发，模型重读自己刚写的代码。
- 每次模型调用都重放完整历史，T09 类任务 19 次调用 = 19 次完整历史重发。

### 做法
- 上下文组装时，对已访问文件（读过/写过）用**状态快照**取代完整内容回放：
  路径 + 行数 + 内容指纹 + 简要摘要，需要细节时再按需回读。
- 快照随文件变更更新（写工具回执的计数已可判定是否变化），避免快照过期。
- 保留「按需回读」通道：模型需要原文时能精确取回对应文件。

### 涉及模块（预估）
- `services/api/src/blank_api/services/agent/context.py`（上下文组装与窗口链）
- `services/api/src/blank_api/services/agent/payload.py`（历史裁剪）
- 文件访问状态缓存（`file_state.py` / `FileStateCache`）

### 验证
- 同批任务对照：改前改后 prompt token / active context 对比，目标峰值降 ≥ 30%。
- 回归：编辑/读后写/交付等既有单测（`test_claude_parity_v24.py` 等）保持全过。

## 四、任务二：压调用次数

### 现状
- T09 类任务 19 次调用。需先定位这 19 次的分布：哪些是重复 read、哪些可合并、
  哪些往返可省、哪些是模型不必要的重试（如解释器替换导致的重试，B6 已修过一处）。

### 做法
1. **诊断**：对 T09 类任务记录每次调用的工具名与参数，统计分布。
2. **合并可并行调用**：无依赖的工具调用放同一批（系统提示已有此约定，检查执行层是否兑现）。
3. **消除冗余往返**：重复读取、读完又写又读等可合并的路径。
4. **提示词与工具表瘦身**：减少不必要的工具说明书字符（34 个工具说明书每轮 22,467 字符是实测成本点）。

### 涉及模块（预估）
- `services/api/src/blank_api/services/agent/graph.py`（执行节点与批次调度）
- `services/api/src/blank_api/services/tools/registry.py`（工具说明书）
- `services/api/src/blank_api/services/agent/prompt_args.py`

### 验证
- T09 类任务调用数从 19 显著下降（目标 ≤ 12），token 同步下降。
- 四任务回归（T01/T25 等）隐藏验收保持 100%。

## 五、并行质量底线（建议与本版并行）

用户目标「质量高过国内产品」的底线，与降 token 不冲突，建议并行推进：

| 项 | 内容 | 影响 |
|---|---|---|
| 1 | `done_when` 判据设为 blocking（判据不过判死，不只记 finding） | 防"没跑校验却声称通过" |
| 2 | 审查前确定性范围（baseSha / 四组路径硬事实） | 审查有稳定输入边界 |
| 3 | 钩子 fail-closed（`HookSpec` 加 `on_failure: block`） | 安全类钩子失败必须阻断 |

这三项是路线图 v2 第二优先级前 3 项，决定质量底线，建议与本版并行或紧随。

## 六、执行顺序

1. **诊断**：T09 类任务 19 次调用分布（半天内出清单）。
2. **任务一**：文件状态快照取代历史回放（先做，覆盖面大）。
3. **任务二**：压调用次数（基于诊断结果动手）。
4. **每步对照**：`evals/compare.mjs` 同批任务出数，达标再进下一项。
5. **质量底线**：与 1-3 并行或在其后收口。

## 七、风险与注意

- 快照取代回放不能丢信息：模型需要原文时必须能精确取回，否则影响编辑正确性。
- 压调用次数不能牺牲正确性：合并批次前确认无依赖，避免工具结果顺序错乱。
- 每步改完跑相关单测 + 真机同批任务对照，不凭文档给结论。
- 真机对照需后端运行（SQLite 模式可跑，无需 Docker）。
