## 0. 一页纸

### 0.1 三条总判断

**判断一：我们的任务生命周期不是"五个阶段"，是"两个节点 + 一个循环"。**

PMP 的过程组按项目时间轴铺开（启动 → 规划 → 执行 → 监控 → 收尾），一个项目跑几个月。
我们的一次任务跑几分钟到几十分钟，而且**执行与监控是同一拍**：每调一次工具，`stall.py`
判失败签名、`progress.py` 判有没有新证据、`graph.py` 判预算——三件事都在同一步里发生，
不是"先执行一段、再监控一段"。所以过程组搬到我们这里要重新画（§1.2），照着时间轴摆会
摆出一个不存在的阶段。

**判断二：十块里只有两块能机器判到底，其余八块是"半个"或"没有"。**

能判到底的两块是**成本**（`cost.py` + `limits.py` + `usage_ledger.py`）和**质量控制**
（`verifier.py` 的 14 项 check）。这两块我们比 PMP 硬——因为 PMP 靠人填报，我们每一步都有回执。
剩下八块里，六块有半成品，四块基本没有（清单见 §5）。

**判断三（最重要）：我们缺的不是十个领域的过程，是一个"基准"对象。**

PMP 的十个领域里，九个都有一个"控制/监督"过程，它们的输入是同一类东西：**一份先前定下的
基准或计划**（通行理解）。
- 控制范围 → 范围基准；
- 控制进度 → 进度基准；
- 控制成本 → 成本基准；
- 控制质量 → 质量测量指标；
- 控制资源 → 资源基准；
- 监督风险 → 风险登记册里的触发条件。

**"控制"在这里等于"对比"**——没有基准就没有对照物，只能测绝对量（这正是 §2.4 的问题）。

我们这些基准一份都没有：没有范围基准（上一份提了 `goal_spec.baseline`，未落地）、
没有工期基准（根本没有工期）、成本只有**天花板**不是**基准**（`cost_limit` 是"最多花多少"，
不是"计划花多少"）、质量指标是模型自己写的判据、资源只有并发上限、风险没有登记册。

**所以"把 PMP 十个领域都做一遍"是错的方向。** 正确的最小动作是：先造一个能承载偏差的
基准对象，十块里的六块会自动长出"控制"来。本文 §6 的门全部围绕这一点。

### 0.2 十个领域总表

| # | 领域 | 我们的现状 | 能机器判到哪一步 | 结论 |
|---|---|---|---|---|
| 1 | 整合 | 半成品：计划有、不落库；变更无影响分析 | 章程字段可判、计划结构半判、变更影响不可判 | 补 baseline + 计划落库 |
| 2 | 范围 | 半成品：`page` check 刚加（见上一份） | 判据可判、"是否这件事"不可判 | 按上一份 T0–T3 |
| 3 | 进度 | 没有：无工期、无真实依赖、无关键路径 | 完成/未完成可判，"按期"不可判 | **只做阻塞图，不做排期** |
| 4 | 成本 | 半成品：有强闸、无事前估算 | 全可判（十块里最硬） | 补 forecast 一个函数 |
| 5 | 质量 | 半成品：QC 硬、QA 有雏形、质量规划空 | 结果可判、过程半判 | 别再加 check 类型，加"返工"信号 |
| 6 | 资源 | 没有：只有并发上限与 token 预算 | 并发/租约可判 | **只做配额，不做资源日历** |
| 7 | 沟通 | 半成品：门很硬、计划没有 | 全可判（且有反骚扰原则） | 保持，别扩 |
| 8 | 风险 | 半成品：应对硬、登记册无 | 识别/应对可判、概率影响不可判 | 登记册只留四字段，且必须是引用 |
| 9 | 采购 | 基本没有 | 只有"要不要联网/装依赖"可判 | **大半不该做** |
| 10 | 干系人 | 没有（单用户） | 参与可判、满意度不可判 | **大半不该做** |

### 0.3 两个直接答案

- **最该立刻做成代码的门**：**开工前的成本预估门**——在 `create_plan` 之后用"计划步数 ×
  历史每步 token 中位数 × 单价"算一次预计花费，超过 `cost_limit` 就在花第一分钱之前让用户做一次
  选择（继续 / 缩范围 / 提上限），落点 `services/agent/cost.py` 新增 `forecast()`，
  调用点在 `services/agent/graph.py:3428` 的 `create_plan_node` 末尾（计划转成结构化数据那段，
  `graph.py:3627` 附近）。理由见 §6.2.1。
- **最不该搬的一块**：**挣值分析（EVM）**。它需要的三个量我们有两个不存在，硬算出来的
  CPI 会奖励"把计划拆得更碎"。替代指标已经在 `harness/evolution.py` 里，见 §4.2。

## 1. 坐标系：一次 Agent 任务到底有几个节点

### 1.1 七个节点（按代码顺序）

| # | 节点 | 代码位置 | 这一段的实质 |
|---|---|---|---|
| N0 | 建任务 | `api/routes/tasks.py` → `schemas/task.py:24-49` | 收 `goal`（原话，不许改写）、`goal_spec`、`acceptance_criteria`、以及**授权**：`max_steps`、权限模式、模型（`provider_id`）；token 预算不在请求里，走全局设置（`settings.py:160`） |
| N1 | 意图判定 | `services/agent/intent.py:163-184` | 分 `answer / advise / act`，产出 2-6 条粗步骤 |
| N2 | 计划生成 | `graph.py:3428` `create_plan_node` → `services/agent/planner.py:74` | 归一化成 `plan_steps`，补 `kind/risk/tools/depends_on/success_condition`，给出 `approval_points` |
| N3 | 执行循环 | `graph.py` 主循环（工具调用）；旁挂 `stall.py` / `progress.py` / 预算段 `graph.py:5620-5700` | 模型调工具、拿回执；**每一步同时被三个哨兵检查** |
| N4 | 验证 | `graph.py` 校验通道 → `services/agent/verifier.py:308` | 14 项事实核对，产出 verdict |
| N5 | 收尾 | `services/agent/delivery.py`（四行交付）、`runtime.py:2132-2146`（落库） | 交付文本 + 状态判定 + 计划/验收结果写回 |
| N6 | 沉淀 | `services/agent/experience.py:162` `admission` | 这次该不该产出经验（四条判据） |

**注意 N6 之前还有一件事**：`graph.py:1127` `ensure_snapshot()` 在动手前抓一份工作区快照
（`services/sandbox/snapshot.py:66`），收尾后由用户手工回滚（`api/routes/tasks.py:754`）。
这在 PMP 里没有对应过程——它是**风险应对的实物化**，不是收尾动作。

### 1.2 与五个过程组的对齐

| PMP 过程组 | 我们对应哪一段 | 对齐度 | 差在哪 |
|---|---|---|---|
| 启动 | N0 + N1 | **形态不同**：章程被拆成"原话 + 目标规格 + 授权参数"三个字段 | 没有"发起人批准"这个动作——用户建任务就是批准 |
| 规划 | N2 | **弱**：计划是"一串步骤"，不是"一组子计划" | 九个知识领域的子计划里，只有范围（done_when）与质量（check）有位置 |
| 执行 | N3 前半（工具真的跑） | **强** | 无 |
| 监控 | N3 每一步的三个哨兵 + `heartbeat.py` | **过强**：PMP 靠周报，我们靠每步回执 | 缺"偏差"这个概念（没有基准可偏） |
| 收尾 | N4 + N5 + N6 | **半**：验收与经验都有，交付确认没有 | 没有"客户签字"环节（单用户产品里就是他自己看） |

**关键改写（我们的改写，不是 PMP）**：PMP 里执行与监控是两个并行过程组；在我们这里它们是
**同一步里的两件事**。这带来一个直接后果——**监控过剩、规划不足**。我们有 10 类失败识别
（`stall.py:41-50`）、4 个空转/重写阈值、3 个预算天花板、1 个心跳巡检，但计划里每个步骤
只有 7 个字段（`plan.py:333-341`：`id / step / status / milestone_id / evidence / output / check`），
**没有产出物路径、没有需求指向、没有估算、没有真实依赖**。**把力气花在计划上，比再加一个哨兵划算。**

### 1.3 为什么"基准"是这十块共用的缺口

把最要紧的六个"控制/监督"过程摊开看，它们要求的输入是同一个东西：

| 控制过程 | 要求的基准 | 我们现在有什么 | 差额 |
|---|---|---|---|
| 控制范围 | 范围基准（SOW + WBS + 字典） | `goal_spec` 的三字段，无 frozen 版本 | 上一份 §6.5 的 `baseline` |
| 控制进度 | 进度基准（含里程碑日期） | `plan_steps[].status`，无日期 | 无 |
| 控制成本 | 成本基准（按时间分布） | `cost_limit` 一个数（默认 0 = 不限） | 无分布、无计划值 |
| 控制质量 | 质量测量指标 | 模型自己写的 `done_when` | 无独立指标 |
| 控制资源 | 资源基准 | 并发 4 / 租约 90 秒 | 无计划用量 |
| 监督风险 | 风险登记册的触发条件 | `step_risk()` 关键词 | 无登记册 |

六个格子，六个"无"。这不是六个独立的缺口，是**同一个抽象缺失**：我们记录"发生了什么"，
不记录"本来应该发生什么"。`evolution.py` 是这个抽象的唯一现成实现——它拿**两段窗口**做对照，
所以它天然有"本来"。这也是为什么 §4.2 的替代指标全在它那儿。

## 2. 五大过程组：逐个落到我们的系统里

### 2.1 启动（Initiating）

| PMP 要求（通行理解） | 我们的对应物 | 有没有 |
|---|---|---|
| 制定项目章程：授权项目存在、授权项目经理动用资源 | `goal` + `goal_spec` + `max_steps` / 权限模式 / 模型（`schemas/task.py:24-49`）+ token 预算（`settings.py:160`） | **有，但是字段不是文档** |
| 识别干系人：谁影响项目、谁被影响、他们的期望 | 单用户产品里退化成"这个用户此刻的标准"——`persona.py:491` 的 `STANDARDS`（严谨/简洁两套，共 6 条可核对条款）；团队模式下才有真名册（`services/team.py` 的 Bot 名册） | **半有** |
| 发起人批准 | 建任务即批准；没有第二个人 | **不需要** |

**判读**：PMP 的章程有法律/组织含义（签字授权）。在 Agent 里它的实质只剩一句：
**这次允许它花多少、动什么、用什么模型**。这四个参数我们现在都有，缺的是"开工前把
这四个数念一遍给用户看"。这不是文档工作，是一个 `startup_check()` 的返回值：

```
objective 非空？ / done_when 至少 1 条？ / token_budget 与 cost_limit 是否都为默认值（=没人想过）？
/ 权限模式是否是 bypass（=没人管）？
```

四项里任意一项是"没人想过"，在 act 任务上弹一次确认卡（复用 `propose_goal`，上一份 §3.3 已定）。

> **这块搬过来是浪费的判断**：项目章程文档、商业论证、效益管理计划、发起人签署流程——
> 一个都不要。我们的"章程"就是四个参数，写成文档只会让模型以为多了一份要遵守的东西。

### 2.2 规划（Planning）

PMP 在这里要求十份子计划（范围/进度/成本/质量/资源/沟通/风险/采购/干系人 + 整合）。逐份看我们有没有位置：

| 子计划 | 在我们系统里的位置 | 形态 |
|---|---|---|
| 范围 | `goal_spec.objective / done_when / constraints / out_of_scope` | **有**（上一份已做到字段级） |
| 进度 | `plan_steps` + `planner.depends_on` | **弱**：无工期、依赖是假的（§3.3） |
| 成本 | `limits.py` 的三个天花板 | **弱**：只有上限，无事前估算（§3.4） |
| 质量 | `plan_steps[].check`（已落地，但只提示不拦）+ `done_when[].check` | **半** |
| 资源 | 无 | **没有** |
| 沟通 | `settings.notify_policy`（全局，非 per-task）+ `dispatch.py:434` | **半** |
| 风险 | `planner.step_risk()` 三档关键词（`planner.py:65`） | **弱**（§3.8） |
| 采购 | `dispatch._tool_policy`（决定给哪些工具） | **形态不同**（§3.9） |
| 干系人 | 无 | **没有** |
| 整合 | `planner.build_plan()` 返回的那个 dict | **有结构、不落库**（上一份断点 1.6） |

**判读**：我们其实是"积分制"规划——每份子计划都被压缩成一个字段或一个函数，散在七八个文件里。
这未必是坏事：**一份子计划的价值等于它里面有几条能被机器读的判据**。九份文档里如果每份只有
一句话有判据，那九份合并成九个字段是对的。

真正的问题只有一个：**`build_plan()` 的输出没有落库**（`runtime.py:2137-2146` 只写
`plan_steps / milestones / goal_spec / acceptance_results`）。于是 `risk / approval_points /
depends_on / rollback_strategy` 这些规划产物**跑完就没了**，事后无法回答"当时计划里的审批点
是哪几个、实际触发了哪几个"。这是整合管理最实的一个缺口，也是 §6 表里"计划落库"那一行的理由。

> **这块搬过来是浪费的判断**：九份子计划文档、规划会议、滚动式规划（rolling wave）的仪式——
> 不要。但**计划结构落库**要做，因为它是唯一能让"计划 vs 实际"可对照的东西。

### 2.3 执行（Executing）

| PMP 要求 | 我们的对应物 | 有没有 |
|---|---|---|
| 指导与管理项目工作 | `graph.py` 主循环 | **有** |
| 管理项目知识 | `experience.py`（准入 + 去重 + 排序 + 过期） | **有，且比 PMP 严** |
| 管理质量（质量保证） | `persona.py:563` `conformance()`——按条款核对交付文本；`harness/evolution.py` 跨任务指标 | **半**（§3.5） |
| 获取资源 / 建设团队 / 管理团队 | `services/subagent.py:107`（并发 4 + Semaphore）、`team.py`（群聊轮次编排） | **形态不同**（§3.6） |
| 管理沟通 | `notify.py:36 should_disturb` + `:62 may_push` | **有，且有反骚扰原则**（§3.7） |
| 实施风险应对 | 审批闸（`permissions.py:623 ask`）、快照（`snapshot.py`）、拒绝（`deny`）、沙箱 | **有**（§3.8） |
| 实施采购 | 装依赖/联网/接第三方 API 的审批 | **半**（§3.9） |
| 管理干系人参与 | 审批卡 + 澄清卡 | **有**（§3.10） |

**判读**：执行组是十块里我们**最不需要向 PMP 学**的一段。理由很直接：PMP 的执行组大半在
解决"人和人之间传话失真"，我们没有传话——工具回执是结构化的。"管理项目知识"那一项我们甚至
比 PMP 严：PMP 只要求"记录经验教训"，我们额外要求**这次值不值得学**（`admission` 四条：
没改动不学、没验证不学、只读不学、失败必须有外部信号）。这条严是有实测依据的——
现有记忆里 79% 是"整任务总结"这种负迁移形状（`experience.py:175-176` 的注释）。

> **这块搬过来是浪费的判断**：团队建设阶段（塔克曼阶梯）、冲突管理、认可与奖励——
> 我们只有一个执行者，没有"团队士气"。团队模式（`team.py`）里只有"发言顺序"，加这些东西
> 就是给一个单轮群聊配 HR。

### 2.4 监控（Monitoring & Controlling）

| PMP 要求 | 我们的对应物 | 有没有 |
|---|---|---|
| 监控项目工作（数据 → 信息 → 报告） | 事件流（数据）→ `usage_ledger.py`（信息）→ `heartbeat.py:82 analyze`（报告） | **有，三级都对得上** |
| 实施整体变更控制 | `update_plan` + `plan_revision`（`runtime.py:2140`） | **弱**：无影响分析、无批准（上一份 §6） |
| 确认范围 | 无 | **没有**（上一份 §5.5） |
| 控制范围 | 无基准 | **没有** |
| 控制进度 | `progress.py`（空转）+ `plan_progress()` | **有，但测的不是进度** |
| 控制成本 | 金额闸（`graph.py:5628`）+ token 预算 + `budget.warning` | **有，且是自建** |
| 控制质量 | `verifier.py` 14 项 | **有**（§3.5） |
| 控制资源 | worker 租约（`worker.py:42` `LEASE_SECONDS=90`）+ 并发上限 | **半** |
| 监督风险 | `stall.py` 10 类识别 + `watchdog.py` | **半** |
| 监督沟通 | `heartbeat.py` 的 `stuck_approval` / `failure_cluster` | **有** |
| 监督干系人参与 | 无（没有满意度信号） | **没有** |

**判读（这一节的中心）**：监控是我们**投入最多、回报最低**的一块。投入多到有 10 类失败
分类、6 个阈值、1 个定时巡检；回报低的原因不在实现，在**没有基准**——所有哨兵回答的都是
"现在是不是异常"，没有一个能回答"偏离计划多少"。

一个具体的例子：`heartbeat.py:32` 判"任务 running 超过 30 分钟"，这是一个**绝对阈值**。
它不知道这个任务计划跑 3 分钟还是 3 小时。如果计划里没有工期，30 分钟这个数就只能靠在
所有任务上取一个折中值，于是简单任务报得太晚、复杂任务报得太早。这不是阈值调得不好，
**是缺了分母**。

> **这块搬过来是浪费的判断**：绩效测量基准、偏差分析（SV/CV 公式）、趋势分析、储备分析——
> 全部依赖基准，而基准不存在。先造基准（§1.3），再谈偏差；否则这些公式只是把"没有"包装成
> "有"。**这一块是本文最该说"不做"的地方，比采购和干系人都更该说。**

### 2.5 收尾（Closing）

| PMP 要求 | 我们的对应物 | 有没有 |
|---|---|---|
| 结束项目或阶段、验收可交付成果 | `verifier.py:308` verdict + `acceptance_results` 落库（`runtime.py:2132`） | **有**（但 verifier 刻意不 blocking 大部分项） |
| 移交可交付成果 | `delivery.py` 四行（完成/改动/验证/需要你） | **有，格式固定** |
| 收集经验教训 → 经验教训登记册 | `experience.py`（准入 + TTL 90 天 + 置信度门槛 0.3） | **有** |
| 经验教训的质量回顾 | `experience.py:688 lint` / `persona.py:835 lint`——专门查"条目自相矛盾/触发词堆太多/否定式写法" | **有，PMP 里没有这个动作** |
| 释放资源 | run 置终态（`queue.py` 的 `TERMINAL_RUN_STATES`）、租约过期被下一个 worker 接手（`queue.py:claim_run` 的 `lease_expires_at` 条件）、产物清理（`maintenance.py` + `artifacts.py` 的 `stats()`） | **有** |
| 归档项目文件 | 事件表 + 快照（留存直到手工回滚） | **有** |

**判读**：收尾这块我们比 PMP 多一个动作——**对沉淀物本身做 lint**。这是有原因的：
经验一旦写错，会被注入到后续任务里当"历史规律"照做，错一条污染一片。PMP 的"经验教训
登记册"没有质量门，因为它假设写的人会负责；我们没有这个假设。

**缺的一块是"确认"**：PMP 的收尾要求客户正式验收，我们只有 `accepted` 这个概念，
没有"用户说了这算过"。上一份 §5.5 的 `scope_review` 是补这一环的一半（机器判"做的是不是
这件事"），另一半（用户点头）在单用户产品里可以简化为一次明确的"就这样"。

> **这块搬过来是浪费的判断**：项目档案移交清单、采购关闭、最终报告——不要。
> 但"验收要有人点头"这一条不能省，它跟文档无关，跟责任有关。

### 2.6 汇总：每个过程组该不该有

| 过程组 | 该不该有 | 以什么形态 | 一句话 |
|---|---|---|---|
| 启动 | **该有** | 一个 `startup_check()` 的返回值，不是文档 | 四个参数念一遍 |
| 规划 | **该有，但要压缩** | 九个字段，不是九份计划 | 计划结构必须落库 |
| 执行 | **已经有，不用加** | 现有循环 | 这一段我们已经超过 PMP |
| 监控 | **该有，但要先有基准** | 偏差，不是绝对阈值 | 没有分母的告警是噪音 |
| 收尾 | **该有，缺"点头"** | verdict + 一次确认 | 已有 lint，PMP 没有 |

## 3. 十大知识领域：能自动化到什么程度

每一节统一四列：**PMP 要求什么 | 我们系统里对应什么（带路径） | 能不能机器判 | 缺什么**。
每节结尾一句"这块搬过来是浪费"的判断。

### 3.1 整合管理

| PMP 要求（通行理解） | 我们对应什么 | 能机器判？ | 缺什么 |
|---|---|---|---|
| 制定项目章程 | `schemas/task.py:24-49` 的三个请求参数（`max_steps` / 权限模式 / 模型）+ 全局 token 预算（`settings.py:160`）+ `goal_spec` | **能**（有/无） | 开工前没人念一遍 |
| 制定项目管理计划 | `planner.py:74 build_plan()` 返回 dict | **能判结构，不能判质量** | **不落库**（`runtime.py:2137` 只写四样） |
| 指导与管理项目工作 | `graph.py` 主循环 | 能 | — |
| 管理项目知识 | `experience.py:162 admission` | **能**（四条判据全确定） | — |
| 监控项目工作 | `usage_ledger.py:118` + `heartbeat.py:82` | **能** | 无基准，只能测绝对量 |
| 实施整体变更控制 | `services/tools/plan.py:47 _update_plan` + `plan_fingerprint()`（`plan.py:535`） | **半**：能判"计划变没变"，判不了"变得对不对" | 影响分析、批准（上一份 §6.3） |
| 结束项目或阶段 | `runtime.py:2132` + `verifier.py` | 能 | 用户确认 |

**判读**：整合管理是"其他九块的中枢"，在我们这儿它退化成了**一个 dict 的生命周期**：
`build_plan()` 造出来 → 状态里传 → 收尾丢掉。它不落库意味着**整合管理在我们系统里没有
历史**——无法回答"这个任务当初计划了几个审批点、实际弹了几个"。

> **浪费判断**：整合管理的"项目管理计划"是一份含九个子计划的复合文档。我们不要复合文档，
> 要的是**那一份 dict 落库**。前者是给人读的，后者是给对照用的。

### 3.2 范围管理（引用上一份，不重写）

一句话现状：范围是十块里唯一做到字段级的，`page` check 已进 `plan.py:70` 与
`verifier.py:272`，剩下的是 `requirements` 列与 `scope_review`（上一份 T3）。
**本文不再展开**，只在 §6 表里保留它对应的两个门（变更影响分析、确认范围）。

### 3.3 进度管理

| PMP 要求 | 我们对应什么 | 能机器判？ | 缺什么 |
|---|---|---|---|
| 定义活动 | `plan.py:257 normalize_steps`（≤12 步），每步已有 `output` / `check` | 能 | 有产出物**文本**，没有产出物**路径**（`output_paths`）；无需求指向 |
| 排列活动顺序 | `planner.py:104`：`depends_on = [上一步 id]` | **能判，但内容是假的** | 真实依赖（§4.1） |
| 估算活动持续时间 | **无** | 不能 | `estimate_min` 不存在——`work_package_problems()` 明确**拒绝**判工时（`plan.py:530-533`："我们没有工时账本，编一个区间只会让模型去凑最安全的数字"） |
| 制定进度计划 | **无** | 不能 | 没有时间轴 |
| 控制进度 | `plan_progress()`（`plan.py:454`）+ `progress.py` 空转哨兵 | 半 | 测的是"有没有进展"，不是"比计划慢多少" |
| 关键路径 | **无** | — | 见 §4.1：**不该做** |

**两个必须分清的东西**：`services/agent/schedule.py:133 parse_when` 是**自然语言定时**
（"明天早上九点"），它决定任务**什么时候开始**；PMP 的进度管理决定**任务内部的活按什么顺序、
各要多久**。两者同名不同义，改这块代码时别混。

`plan_progress().percent` 是"完成步骤数 / 总步骤数"。这不是进度，是**打勾比例**：
把一步拆成三步，percent 的分母变了，进度条会**倒退**。这是可以接受的（用户看的是"还剩几步"），
但绝不能拿它当"完成百分比"去做任何计算（EVM 就死在这上面，§4.2）。

> **这块搬过来是浪费的判断**：甘特图、里程碑日期、进度基准、浮动时间计算——
> 全部不要。一次任务没有日历。要的只有一样：**依赖是不是真的**。

### 3.4 成本管理（重点：我们已有金额闸）

| PMP 要求 | 我们对应什么 | 能机器判？ | 缺什么 |
|---|---|---|---|
| 估算成本 | **无** | 不能 | **事前估算**（§6.2.1） |
| 制定预算（含储备） | `limits.py:26 DEFAULT_TOKEN_BUDGET=1.5M`；`settings.py:101 cost_limit=0.0`（默认不限，上限 1e6） | 能 | 只有上限，无计划值；无储备概念 |
| 控制成本 | `graph.py:5628` 金额闸 + `:5635` `budget.exceeded` + `:5672-5676` `budget.warning`（85% 处） | **能，且分三段计价** | per-step / per-model 归集 |
| 成本核算（钱变成了什么） | `usage_ledger.py:42 bucket_of`：`delivered / advised / wasted / running` | **能** | — |
| 成本绩效（每产物成本） | `usage_ledger.py:93 tokens_per_file`、`:95 effective_share` | **能** | 样本不足时别下结论（`evolution.py:29`） |

**这块是全系统最硬的**，值得说清它为什么硬：

1. **三段计价**（`cost.py:71`）：未命中缓存的输入、缓存读、输出分开算。只乘一个综合价，
   在长上下文场景会偏出好几倍——而长上下文恰恰是最费钱的那类任务。
2. **估价不是账单**：事件字段叫 `estimated_cost`（`graph.py:5646`），因为价目表是用户填的，
   可能过期。这个命名纪律防止有人拿它对账。
3. **默认关**（`cost_limit=0`）：没有价目表就凭空算钱，等于编一个数去吓人。

**缺的那一块恰恰是 PMP 成本管理的第一步**：`estimate_cost()` 是**事后**把 usage 折成钱，
`forecast()` 不存在。所以用户设了"最多 2 块"，只能在已经花到 2 块时才知道——那时钱已经花了。
这是 §6.2.1 那个门的全部理由。

**一个数字**：`ModelUsage` 有 `node` 字段（`models/model_provider.py:232`），所以能按
**图节点**归集（create_plan / execute / validate / finish），但**不能按计划步骤归集**——
没有 `step` 字段。这意味着"第 3 步花了多少钱"现在答不出来。要不要加，见 §6 表最后一行。

> **浪费判断**：成本基准、S 曲线、储备分析、资金限制平衡——不要。我们要的是"开工前一个数、
> 收尾后一个归因"，不是一条曲线。

### 3.5 质量管理

| PMP 要求 | 我们对应什么 | 能机器判？ | 缺什么 |
|---|---|---|---|
| 规划质量管理（指标 + 标准） | `done_when[].check` 四类（`plan.py:80`）+ `AGENTS.md` 的判据约定 | 半 | 判据是模型写的，没人审"够不够" |
| 管理质量（质量保证：审过程） | `persona.py:563 conformance()`（按 6 条展开条款核对交付）+ `evolution.py` 的跨任务指标 | **半** | conformance 判的是**交付文本**，不是过程 |
| 控制质量（QC：验结果） | `verifier.py:19-34` 的 14 项 check | **能** | 大部分不 blocking（刻意的） |
| 返工成本 | `remediation.py`（环境缺口推回，上限 2 次）；`planner.py:18 MAX_PLAN_REVISIONS=3` | 能 | 没有"返工率"这个指标 |
| 质量成本（COQ） | 上一份 §2.1 算过一次（预防 3-6k vs 返工 69k token） | 推算 | 没进账本 |

**一个有用的区分**（我们的改写）：PMP 的质量保证与质量控制，在我们这儿对应的是**两个不同
的时间尺度**：

- **QC = 单任务、事后、看事实** → `verifier.py`。它回答"这一份交付有没有硬伤"。
- **QA = 跨任务、长期、看统计** → `evolution.py`。它回答"这个机制有没有让整体变好"。

这个改写有好处：QA 不再需要"质量审计员"，只要有足够样本。代价是**QA 有延迟**——
样本 <20 不下结论（`evolution.py:29`），所以一个刚上线的机制，一周内无法判断好坏。

**质量规划是空的**：`done_when` 的 check 由模型在规划时自己写，没有任何东西检查
"这些判据能不能证明目标"。上一份 §4.4 的 `check_shape_problems()` 就是补这一格，
但它只查**形态**（否定式/首屏/模糊词），查不了**充分性**——那需要人。

> **浪费判断**：质量审计、过程改进模型（PDCA 全套）、质量屋——不要。要的只有一件事：
> **返工率**。它是唯一能把"质量差"换算成"钱"的指标，而且数据我们已经有了
> （同 thread 连续两轮同 objective 的比例，上一份 §8.1 的 `rework_rate`）。

### 3.6 资源管理

| PMP 要求 | 我们对应什么 | 能机器判？ | 缺什么 |
|---|---|---|---|
| 估算活动资源 | **无** | 不能 | 没有"这个任务要几个子代理/多少并发"的估算 |
| 获取资源 | `subagent.py:107 MAX_PARALLEL_AGENTS=4` + `Semaphore`（`:2310`）；模型/供应商选择 | **能** | 无 per-model 配额 |
| 建设/管理团队 | `team.py`（Bot 名册 + 发言顺序）；`persona.py`（用户习惯） | 形态不同 | 无（也不需要） |
| 控制资源 | `worker.py:42 LEASE_SECONDS=90`、`queue.py` 认领、`loadstats.py` | **能** | 无"谁在占什么"的视图 |
| 资源平衡 | **无** | 不能 | 触发器的并发没有统一排队 |

**判读**：我们没有"资源"，只有**配额**。这是对的——资源管理在 Agent 里退化成三个数：
并发几个、每个模型多少 token、一个 run 占多久的租约。前两个有，第三个有但没有配额。

缺的那一个值得补：**per-model 配额**。现在 `token_budget` 是全局一个数（默认 1.5M），
不管用的是贵模型还是便宜模型。用户拿一个 1.5M 的预算跑推理模型，和跑小模型，是两件完全不同
的事——而金额闸能区分（靠价目表），token 闸不能。

> **浪费判断**：资源日历、资源直方图、资源平衡算法、RACI 矩阵——一个都不要。
> RACI 尤其荒谬：一个执行者，四个角色全是它。

### 3.7 沟通管理

| PMP 要求 | 我们对应什么 | 能机器判？ | 缺什么 |
|---|---|---|---|
| 规划沟通管理 | `dispatch.py:66-70` 四策略（silent / milestone / approval_only / always）+ `:434 _notify_policy` 按意图与优先级选 | **能** | 是**全局设置**，不是 per-task 计划 |
| 管理沟通 | `notify.py:36 should_disturb`（该不该打扰）+ `:62 may_push`（允不允许主动发）+ `delivery.py` 四行 | **能** | — |
| 监督沟通 | `heartbeat.py:82` 的 `stuck_approval`（审批压太久）、`failure_cluster`（同类失败扎堆） | **能** | — |

**这一块我们有一条比 PMP 硬的原则（我们的改写，有实测依据）**：`may_push()` 默认**不发**。
规则原文在 `notify.py:65-67`：

> 做了定时任务、用户有这个需求，那就发；没做定时发送的任务，不要自主发。

代码把"默认的 approval_only"也算作"不发"，理由是：用户配了一个通道，意思是"我能从这里回话"，
不等于"你可以主动找我"（`notify.py:76-78`）。PMP 的沟通管理假设"沟通越充分越好"，
我们的实测结论正相反：**后台任务刷屏 → 用户关通知 → 连"审批等你点"都收不到**（`notify.py:4-5`）。

这条原则是十块里唯一一条**推翻 PMP 假设**的。它值得保留，而且值得在别的地方复用
（比如 §6 的"弹卡"决策都应该走同一个"打扰预算"）。

> **浪费判断**：沟通管理计划、干系人沟通需求分析、沟通渠道数公式（n(n-1)/2）——不要。
> 我们只有一个接收者，渠道数是 0。

### 3.8 风险管理

| PMP 要求 | 我们对应什么 | 能机器判？ | 缺什么 |
|---|---|---|---|
| 识别风险 | `stall.py:41-50` 十类失败识别；`progress.py` 空转；`unknowns.py`（写前查事实出处）；`remediation.py`（环境缺口） | **能**（且是"已发生"的风险） | 识别的是**症状**，不是**风险** |
| 定性风险分析 | `planner.py:65 step_risk()` 三档（关键词命中 `_HIGH_RISK_MARKS`） | 半 | 关键词判"这一步危险吗"，判不了"多可能、多严重" |
| 定量风险分析 | **无** | 不能 | 无概率、无影响值 |
| 规划风险应对 | `planner.py:117` `approval_points = [risk == high 的步骤]`；`permissions.py:623 ask`；快照回滚；`deny` | **能**（有一半） | 应对与风险的**绑定**是隐式的（靠 risk 字段），不是显式的 |
| 实施风险应对 | 审批卡、`sandbox/snapshot.py:207 restore`、`permissions.py:137 IRREVERSIBLE` 正则 | **能** | 回滚是**手工**的（`api/routes/tasks.py:754`） |
| 监督风险 | `stall.py` 熔断（同签名失败 2 次拦）、`progress.py` 提醒（4 步无证据）、`watchdog.py` | **能** | — |

**最值得注意的一条**：`planner.py:117` 已经在做"高危步骤自动成为审批点"——这是风险应对规划
在我们系统里唯一一处真实落地，而且它**不是给模型看的表**，是 `approval_points` 这个数组，
`graph.py` 真的会读它。这条设计比 PMP 的风险登记册更实：PMP 登记册里写"责任人：张三"，
我们这里写的是"这一步必须有人点批准"，而那个人真的会被弹卡。

它的问题只有一个：**判定靠关键词**（`_HIGH_RISK_MARKS` 里有"删除/安装/部署/发布/push/上传"等
17 个词，`planner.py:37-40`）。"把 index.html 里的一个 div 删掉"会命中"删除"→ 高危 → 弹卡。
这是可接受的（宁可多问），但要承认它是**词表**不是**分析**。

> **浪费判断**：风险分解结构（RBS）、概率影响矩阵（P×I 打分）、风险类别学、
> 风险偏好/容忍度——全部不要。概率没有数据来源（我们每类任务样本 <20，`evolution.py:29`），
> 打分就是编。详见 §4.3。

### 3.9 采购管理

| PMP 要求 | 我们对应什么 | 能机器判？ | 缺什么 |
|---|---|---|---|
| 规划采购管理（自制或外购） | `dispatch.py:412 _tool_policy`（这个任务给哪些工具）；技能市场 `skill_market.py:44 ALLOWED_HOSTS`（能装什么） | 半 | 没有"这件事该自己算还是调外部"的判据 |
| 实施采购（选卖方、签合同） | **无** | 不能 | — |
| 控制采购（履约、变更、索赔） | 无（第三方 API 失败只算工具失败） | 不能 | — |
| 结束采购 | 无 | 不能 | — |

**这一块只有一处真实对应**：**当模型要装依赖、联网、调第三方 API 时，要不要批**。
判据已经散在三处：`permissions.py:137` 的 `IRREVERSIBLE` 正则（含安装/删除/发布类命令）、
沙箱的网络开关、`IRREVERSIBLE` 之外的 `_HIGH_RISK_MARKS`。这三处没有统一口径，
是这一块唯一值得做的小事（把"外购"收成一个判断函数）。

**合同没有对应物，也不该有**：我们和第三方之间没有可执行的约定，只有"调用失败就重试/换路"。
把 SLA、验收条款、违约写进来，是给一个 HTTP 请求配法务。

> **浪费判断**：整块采购管理（四个过程里三个用不上）。自制外购分析可以留一个函数，
> 合同、卖方选择、索赔、采购关闭——全部不要。

### 3.10 干系人管理

| PMP 要求 | 我们对应什么 | 能机器判？ | 缺什么 |
|---|---|---|---|
| 识别干系人 | 单用户：`persona.py`（偏好 + 6 条标准）；团队模式：`team.py` 的 Bot 名册 | 半 | 没有"还有谁关心这个结果" |
| 规划干系人参与 | `propose_goal` 卡（`services/tools/goals.py:75`）、`ask.py`（最多 4 问） | **能**（问几次、问什么） | 参与程度不可判 |
| 管理干系人参与 | 审批卡、澄清卡、`notify.py` | **能** | — |
| 监督干系人参与 | 无 | 不能 | 满意度、支持度都没信号 |

**判读**：单用户产品里，"干系人识别"退化成**"这个人此刻要什么"**。`persona.py` 做的是
从他的话里抽"标准"（严谨/简洁），这是唯一可自动化的部分，而且它有一条纪律写得很对：
展开的条款是**我们的理解**，不是他的原话，所以只报告、不拦（`persona.py:487-490`）。

真正有意思的是**团队模式**：`team.py` 里有真名册、有 @ 点名、有 PASS 语义——这是十块里
唯一出现"多个利益方"的地方。但它仍不是 PMP 的干系人管理：那些 Bot 没有独立的利益，
只有发言顺序。

**能算的替代指标**：`evolution.py` 的 `denial_rate`（驳回率）与 `explained_denial_rate`
（需要解释的驳回）。驳回率高说明我们问得不对，不是用户难伺候——这是唯一能把"干系人
不满意"变成数的东西。

> **浪费判断**：权力/利益方格、干系人参与评估矩阵（当前/期望参与度）、干系人登记册——
> 不要。我们只有一个权力级别：能点批准的那个人。

## 4. 三个必须回答的问题

### 4.1 关键路径在 Agent 任务里有意义吗

**没有，而且是结构性地没有。**

关键路径法（CPM，通行理解）是在活动网络图上找**最长路径**，它决定项目最短可能工期；
关键路径上活动的总浮动为零——晚一天，整个项目晚一天。

我们的执行是**单线程串行**：一个 `AgentRun` 由一个 worker 认领（`queue.claim_run`），
一个模型一次只产出一批工具调用。于是活动网络图退化成一个**全序链表**，最长路径 = 全部活动，
"关键路径"这个词的信息量归零。算它等于把步骤数再数一遍。

**但 CPM 有两个副产品在我们这儿是真问题**：

**副产品一：依赖的真实性。** `planner.py:104` 写的是
`"depends_on": [previous_id] if previous_id else []`——**每一步都依赖上一步**。
这不是依赖，这是顺序。后果有三个：

1. **失败影响面无法计算**：任何一步失败，下游全部"受影响"，等于没有定位。
2. **无法并行**：`subagent.py` 支持 4 个并发，但计划没告诉它哪几步可以同时做，
   所以并行只能靠模型临场判断。
3. **无法跳过**：一步做不了，无法判断"跳过它还能不能交付"。

**副产品二：浮动时间。** 哪些步骤可以晚做、可以不做而不影响验收——这在上一份的
`priority: could` 需求上有真实对应物，但现在没有结构承载。

**替代方案：阻塞依赖图（blocking DAG，我们的改写）。**

边只在一种情况下存在：**B 的输入是 A 的输出**。判据要可机器判，用**现在已经有**的字段：

| 边成立的判据 | 用哪个字段 | 确定性 |
|---|---|---|
| B 的 `check.path` / `check.cmd` 出现在 A 的 `output` 文本里 | `output` 是自由文本 | **半自动**（字符串包含，误判率高） |
| B 的 `step` 文本里指名 A 的产物 | 文本匹配 | **半自动**，只做提示 |
| 其余 | — | **无边** |

一条排除项：**两条 check 指向同一路径不算依赖**，那是重复检查（`WP_DUP_CHECK`，
`plan.py:565` 已在拦）。依赖的方向是"B 用 A 的产物"，不是"A 和 B 看同一个文件"。

**要让它确定性，只差一个字段**：`output_paths`（工作区相对路径，≤5 个）。加了之后判据变成
"B 的 `check.path` ∈ A 的 `output_paths`"，纯集合运算，无歧义。这是 §6 表 #2（门 B）的实际工作量——
**不是写判据，是补一个字段**。

它支撑三件事，每件都是现在做不了的：

1. **失败影响面** = 下游可达集合。"这条命令挂了要重做几步"变成可数的数。
2. **并行可行性** = 同层无边的步骤可并发（受 `MAX_PARALLEL_AGENTS=4` 限制）。
3. **可跳过性** = 不在任何 `priority=must` 需求路径上的步骤，允许 `cancelled` 而不是失败。

**明确不做**：关键路径计算、浮动时间计算、进度压缩（赶工/快速跟进）。前两个在单线程下
恒等于平凡解，第三个需要"加人"，我们没有第二个人——加子代理是加**并行度**不是加**工期弹性**，
这两件事在 CPM 里是不同概念。

> **一句话**：把"关键路径"换成"阻塞图"，收益从"算工期"变成"算重做成本 + 找并行机会"。
> 前者我们没有日历，后者我们真的有 4 个并发槽。

### 4.2 挣值分析（EVM）能不能套

**不能。三个量里两个不存在，剩下那个口径也不对。**

EVM 的三个基本量（原文规定，PMBOK 成本管理）：

| 量 | 定义 | 我们有没有 |
|---|---|---|
| PV（计划价值） | 到某个时间点**按计划应该完成**的工作的预算成本 | **没有**。需要"成本基准按时间分布"，我们只有 `cost_limit` 一个上限，而且默认是 0（不限） |
| EV（挣值） | **实际完成**的工作的预算成本 | **没有可信值**。`plan_progress().percent` 是打勾比例，不是工作量加权；而且分母随计划改版而变（`plan_revision`），拆一步就倒退 |
| AC（实际成本） | 实际发生的成本 | **有**，但只在配了价目表时才是钱（`cost.py:80-81`：无单价时 `priced=False`、金额恒为 0）；否则只有 token |

于是：

- `CPI = EV / AC` —— 分子是假的；
- `SPI = EV / PV` —— 两个都是假的；
- `EAC / ETC`（完工估算/尚需）—— 需要"剩余工作按当前速率继续"的假设。我们的任务方差
  远大于均值（一条任务可能 2 步，也可能 116 步；`limits.py:18-24` 的注释里就有一次
  116 步、4M token 的实例），这个假设不成立。

**最危险的一点**：如果硬凑一个 CPI = "完成步骤数 / token"，它会**奖励把计划拆碎**。
20 步的计划比 5 步的计划 CPI 高四倍，即使两件事完全一样。这是典型的指标被优化——
上一份 §4.1 已经算过拆分的管理税，这个指标会反向补贴它。

**替代指标（全部已在 `harness/evolution.py` 的 `DIRECTION` 表里）**：

| EVM 想回答的问题 | 我们用什么答 | 位置 | 方向 |
|---|---|---|---|
| 钱有没有变成东西 | `effective_share`（delivered 桶占比） | `usage_ledger.py:95` | 越高越好 |
| 每个产物的成本 | `tokens_per_file` | `usage_ledger.py:93` | 越低越好 |
| 单任务总花费 | `tokens_per_task` | `evolution.py:40` | 越低越好 |
| 返工了多少 | `rework_rate`（上一份 §8.1 提出） | 待加 | 越低越好 |
| 交付被接受的比例 | `acceptance_rate` / `success_rate` | `evolution.py:36-38` | 越高越好 |
| 花的钱里多少是废的 | `wasted` 桶占比 | `usage_ledger.py:42-48` | 越低越好 |
| 我们问得对不对 | `denial_rate` / `explained_denial_rate` | `evolution.py:43-44` | 越低越好 |
| **还要多久 / 还要多少钱** | **不回答** | — | — |

最后一行是诚实的部分：EVM 的预测能力（EAC/ETC）我们不做。预测需要稳定的速率，而我们
最贵的失败恰恰是"速率突然崩掉"（空转、上下文腐烂、`restart.py` 的 60k 阈值）。用平稳假设
预测一个会崩的系统，得到的数比没有更糟——它会让人以为有底。

**一个例外值得说**：`evolution.py` 的**窗口对照**（前后两段，样本 ≥20）是 EVM 真正的
替代品，而且比 EVM 强：EVM 拿"计划"当基准，我们拿"上一个自己"当基准。计划是模型写的，
自己是可以被证伪的。

> **一句话**：EVM 是为"人月"和"日历"设计的。我们的单位是 token，没有日历，也没有稳定的
> 速率。硬套得到的三个小数（CPI/SPI/EAC）没有一个能指导决策。

### 4.3 风险登记册能不能落成真实结构

**能，但只能留四个字段。第五个（概率）开始就是编。**

PMP 的风险登记册字段（通行理解）：ID、风险描述、类别、**概率**、**影响**、优先级（P×I）、
应对策略、责任人、触发条件、状态。

逐字段判"我们有没有数据来源"：

| 字段 | 数据来源 | 判定 |
|---|---|---|
| ID | 生成 | 真 |
| 描述 | 模型写 | 真（但只是文字） |
| 类别 | 可从 `stall.KIND_*` 映射 | 真 |
| **概率** | 需要同类任务的历史频率 | **假**：每类样本 <20（`evolution.py:29`），填 0.3 就是编 |
| **影响** | 需要"这一步失败的代价" | **半**：能用 token/返工轮数估，但样本内方差极大 |
| 优先级 P×I | 两个假数相乘 | **假**（而且比单个假数更危险，因为它看起来像算过的） |
| 应对策略 | 映射到已有闸门 | **真**（见下） |
| 责任人 | `system` / `user` 两值 | **真** |
| 触发条件 | 映射到已有判定器 | **真** |
| 状态 | 由触发条件求值 | **真** |

所以 v1 登记册只留四样：`{level, trigger, response, owner}`。关键是后两个必须是**引用**，
不是自由文本：

**`trigger` 必须来自这张清单（全部已存在于代码里）**：

| trigger id | 判定器 | 位置 |
|---|---|---|
| `tool.same_signature_fail` | 同签名失败 2 次 | `stall.py:59 SIGNATURE_FAIL_LIMIT` |
| `tool.same_kind_fail` | 同工具同类失败 3 次 | `stall.py:60 SAME_KIND_LIMIT` |
| `progress.no_new_evidence` | 连续 4 步无新证据 | `progress.py:34 IDLE_LIMIT` |
| `progress.rewrite_unverified` | 同文件重写 3 次未验证 | `progress.py:31 REWRITE_LIMIT` |
| `budget.tokens` | token ≥ 预算 | `limits.py:26` |
| `budget.cost` | 金额 ≥ 上限 | `cost.py:107` |
| `budget.steps` | 步数用完 | `graph.py:5629` |
| `approval.expired` | 审批超 TTL | `worker.py:113` |
| `env.missing_command` | 命令不存在 | `stall.py:45 KIND_ENV_MISSING` |
| `path.outside_workspace` | 越界写入 | `stall.py:48 KIND_PATH` |
| `fact.no_source` | 写前查不到事实出处 | `unknowns.py` |
| `delivery.incomplete_claim` | 交付自述未完成 | `verifier.py:50-56` |

**`response` 必须来自这张清单（全部已实现）**：

| response id | 动作 | 位置 |
|---|---|---|
| `ask_user` | 弹审批卡，任务暂停 | `permissions.py:623` |
| `deny` | 直接拒绝这条调用 | `permissions.py:629` |
| `snapshot` | 动手前留全量快照 | `graph.py:1127` |
| `restore` | 用户手工回滚 | `sandbox/snapshot.py:207` |
| `block` | 熔断，第三次同类调用直接拦 | `stall.py:309` |
| `advise` | 注入一条提醒（不拦） | `progress.py:95` |
| `wrap_up` | 要求收尾 | `graph.py:5672-5692` |
| `push` | 主动通知用户 | `notify.py:62` |
| `pause` | 转后台/等待 | `dispatch.py` |

**校验器 `risk_register_problems()`（确定性，纯函数）**：

```
rule 1: trigger 不在 TRIGGERS 表里        → RISK_UNKNOWN_TRIGGER
rule 2: response 不在 RESPONSES 表里      → RISK_UNKNOWN_RESPONSE
rule 3: level == "high" 且 response 为空  → RISK_NO_RESPONSE（这是唯一该拦的一条）
rule 4: 同一 trigger 在同一计划里出现 >2 次 → RISK_DUPLICATE（合并，别刷表）
```

**这就是"不是写给模型看的表"的判据**：每一行的 `trigger` 和 `response` 都能在代码里
`grep` 到；填不出来的风险不是风险，是**担心**，不应该进登记册。这条判据比任何字段设计
都重要——它把"风险管理"从写作练习变成了引用检查。

**明确不做**：风险分解结构（RBS）、概率影响矩阵、风险数据质量评估、风险审计、
储备分析。理由同 §4.2：没有数据来源。

> **一句话**：登记册能落真，前提是**不许写自由文本**。一旦允许写"这个方案可能不稳定"，
> 它就退化成一张给模型看的表，而且模型会开始为它编概率。

## 5. 存量盘点：哪几块是半成品，哪几块没有，哪几块不该做

### 5.1 半成品（六块）：各差最后一步

| 领域 | 已有的硬东西 | 差的那一步 | 差在哪一行 |
|---|---|---|---|
| 整合 | 计划结构 `build_plan()` | **落库** | `runtime.py:2137-2146` 不写 plan_manifest |
| 范围 | `page` check + verifier 逐条核对 | 需求实体（RTM 一端） | 上一份 T3 |
| 成本 | 金额闸 + 三桶账本 | **事前估算** | `cost.py` 无 `forecast()` |
| 质量 | 14 项 QC + 准入 | 返工率指标 | `evolution.py` 无 `rework_rate` |
| 沟通 | `may_push` 反骚扰门 | 无（这块已经够了） | — |
| 风险 | 高危 → 审批点（真闸） | 应对与风险的**显式绑定** | `planner.py:117` 靠 risk 字段隐式传 |

### 5.2 基本没有（四块）：为什么不建议补全

**先把话说准**：这四块不是零，是**只有监控侧、没有管理侧**——进度有空转检测没有工期，
资源有并发上限没有估算，采购有工具白名单没有取舍判据，干系人有 `persona` 没有识别。
缺的恰好都是 PMP 里「管理」那一半（基准、估算、计划），而那一半都需要日历或第二个人。

| 领域 | 缺什么 | 补全的代价 | 建议 |
|---|---|---|---|
| 进度 | 工期、真实依赖、进度基准 | 需要日历模型 + 稳定的步骤粒度 | **只补阻塞图（§4.1）** |
| 资源 | 估算、配额、占用视图 | 需要跨任务调度器 | **只补 per-model 配额** |
| 采购 | 自制外购判据、履约 | 需要外部依赖的可观测性 | **只把三处高风险判断收成一个函数** |
| 干系人 | 识别、满意度 | 需要第二个真人 | **不做**（团队模式另论） |

### 5.3 不该做的清单（照搬 PMP 会变成负担的部分）

按"搬过来会怎样"排序，从最糟到最轻：

| # | 不该做 | 搬过来会怎样 |
|---|---|---|
| 1 | **EVM（PV/EV/AC、CPI/SPI、EAC/ETC）** | 产出三个精确到小数点的假数；CPI 会奖励拆碎计划（§4.2） |
| 2 | **绩效测量基准 + 偏差分析** | 基准一个都没有，公式全部空转（§1.3、§2.4） |
| 3 | **CPM 关键路径 + 浮动时间** | 单线程下恒等于全部步骤，算了等于没算（§4.1） |
| 4 | **风险概率/影响矩阵（P×I）** | 没有样本来源，填数就是编（§4.3） |
| 5 | **九份子计划文档** | 每份只有一两句有判据，剩下是噪音，还占上下文 |
| 6 | **ITTO（输入/工具与技术/输出）** | 这是培训骨架，不是代码结构 |
| 7 | **RACI 矩阵** | 一个执行者，四个角色全是它 |
| 8 | **权力/利益方格、干系人参与评估矩阵** | 只有一个权力级别 |
| 9 | **合同/采购/索赔/采购关闭** | 给 HTTP 请求配法务 |
| 10 | **甘特图、资源日历、资源直方图** | 没有日历，没有人 |
| 11 | **团队建设阶段（塔克曼）、冲突管理、认可奖励** | 没有团队士气 |
| 12 | **质量审计、PDCA 全过程、质量屋** | 审计员不存在 |
| 13 | **项目章程文档、商业论证、效益管理计划** | 章程就是三个授权参数 + 一个预算（§2.1） |
| 14 | **收尾的档案移交清单、最终报告** | 事件表已经是档案 |

**一条判断规则**（可以用来否决以后所有"要不要加个 PMP 概念"的提议）：

> 一个 PMP 概念值得进代码，当且仅当它满足下面两条之一：
> ① 它有一个**已有的判定器**可以复用（trigger）；
> ② 它有一个**已有的闸门**可以绑定（response）。
>
> 两条都不满足的，写进文档是知识，写进代码是负债。

### 6.2 三个门的具体形状

#### 6.2.1 门 A：开工前的成本预估（表 #1，最该做的那个）

**为什么是它**：

1. `cost.py` 现在只回答"已经花了多少"，不回答"还要花多少"。用户设 `cost_limit=2`，
   闸门在花到 2 元时触发——那时钱已经花完，闸门只能做善后，不能做决策。
2. 估算所需的数据**全都有**：计划步数（`len(plan_steps)`，上限 12，`plan.py:36`）、
   历史每步 token（`ModelUsage` 按 `task_id` 聚合 ÷ `Task.steps_used`）、单价（`settings.budget.pricing`）。
3. 它**不需要新表、不需要新节点**，只在 `create_plan_node` 末尾加一次调用 + 一次事件。
4. 它直接对着最贵的那个桶：`usage_ledger` 的 `wasted`。开工前说"这个计划预计 6 元，你的上限是 2 元"，
   用户改一句范围就能省下 4 元；开工后只能看着它烧完。

**形状**（放 `services/agent/cost.py`）：

```python
def forecast(
    steps: int,
    *,
    per_step_tokens: int = 0,      # 历史中位数，0 = 用内置保守值
    fixed_tokens: int = 6_000,     # 意图判定 + 收尾两次调用
    pricing: dict | None = None,
    provider: str = "",
    model: str = "",
) -> dict:
    """预计这次要花多少。返回形状与 estimate_cost 一致，多一个 basis。

    basis 说明这个数是怎么来的——用户看到"预计 6.2 元"必须能问"凭什么"。
    per_step_tokens 拿不到历史时用 DEFAULT_PER_STEP_TOKENS，并在 basis 里写明是默认值，
    不许静默用一个数冒充测算。
    """
```

调用点在 `create_plan_node` 末尾（`graph.py:3627` 那段把步骤转结构化计划之后），行为：

```
预计金额 ≤ cost_limit          → 什么都不做（不打扰）
预计金额 > cost_limit          → 发 budget.forecast 事件 + 一次三选一确认卡
cost_limit == 0（不限）        → 只发事件，不弹卡（用户没设上限，就是不想被管）
预计无单价（priced=False）     → 只报 token 预估，不报钱
```

**不做什么**：不拦截。它是一次**通报**，不是一次**拒绝**——用户可能就是要花 6 元。
把它做成拦截，就会在"任务本来能成"的情况下把钱省成了功能缺失（`progress.py:20-22`
对"只提醒不拦"的理由同样适用于这里）。

**估算精度要老实说**：`per_step_tokens` 的方差很大（一条任务 2 步也可能 116 步，
`limits.py:17-19`）。所以 basis 里要写区间，不是写一个精确值：
"预计 4–9 元（按最近 30 天每步 29k token 的中位数，实际范围 12k–110k）"。

#### 6.2.2 门 B：依赖真实性（表 #2）

**判据**：`plan_steps[i].depends_on` 里每一条边，必须能被一个事实支持——
A 的产物出现在 B 的 `check.path`（或 B 的 `check.cmd`）里。**现在 `output_paths` 还不存在，
所以这条判据只能退化成"B 的 `output` 文本里出现了 A 的路径"**，是半自动；补上字段之后才是
纯集合运算。否则这条边就是"顺序"冒充"依赖"。

**为什么值得做**：`planner.py:104` 现在生成的是一条链，等于告诉系统"全序"。全序让
§4.1 的三件事全部失效（影响面、并行、可跳过）。改成真图之后，`delegate` 才有依据决定
哪几个子代理可以同时派；而并发槽（4 个）现在是浪费的——因为没有可信的"可以并行"信号。

**为什么只是 S**：最硬的一步是给 `normalize_steps`（`plan.py:333-343`）加一个 `output_paths`
字段，判据本身是集合运算。**没有这个字段时门 B 只能做半自动文本匹配**，所以它排在门 A 之后。

**一个已经存在的半成品要提一下**：`work_package_problems()`（`plan.py:517`）已经在查
"每步有没有 output / check、有没有重复 check"，并且已经接进 `update_plan`
（`tools/plan.py:77`）——但它**只提示不拦**（`tools/plan.py:73-88` 的注释写明：判据形态是新的，
一上来打回会让模型凑一句废话）。门 B 是它的下一档：从"提示"变成"打回"，前提是先有
`output_paths`，否则打回依据是字符串包含，误伤会很多。

#### 6.2.3 门 C：返工熔断（表 #11）

**判据**：同一 `thread_id` 下，同一个 `objective`（`goal_spec.objective` 逐字相同）连续
`failed` 两次 → 第 3 次不许自动开始，必须问用户。

**为什么**：`rework_rate` 是唯一能把"质量差"换成钱的指标（上一份 §8.1），但现在它只被
**统计**，没有被**使用**。熔断是把统计变成动作的最小方式。

**为什么不做"自动重试"**：模型重试同一目标，大概率重演同一失败——`restart.py` 的阈值
（30 步 / 60k token / 8 步无证据）说的是同一件事：**原地重复不是努力**。

### 6.3 顺序与工作量

| 阶段 | 做什么 | 为什么排这个位置 |
|---|---|---|
| **第一步** | 表 #1（成本预估，门 A）+ 表 #9（异常步） | 两个都只改 `cost.py` / `graph.py` 一处，不改数据结构；立刻能看见"钱" |
| **第二步** | 计划结构落库（§2.2 的缺口）+ 表 #3（高危必须有应对） | 一次迁移 + 一处落库；它是后面所有"计划 vs 实际"对照的前提 |
| **第三步** | 表 #2（依赖真实性，门 B）+ 表 #4（变更影响） | 需要先给 `plan_steps` 加 `output_paths`，才谈得上确定性 |
| **第四步** | 表 #11（返工熔断，门 C）+ `rework_rate` 进 evolution | 要先有第二步的历史数据，才判得了好坏 |
| **不做** | 表 #13（per-model 配额）以外的资源管理 | 见 §5.2 |

**一条纪律**：以上每一个门都必须满足 §5.3 那条判断规则（有 trigger 或有 response）。
写不出 `trigger` 的门，说明它其实是"希望模型注意"，那应该进提示词，不该进代码。
