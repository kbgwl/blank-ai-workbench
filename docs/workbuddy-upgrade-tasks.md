## 一、产品目标

Blank AI 不是普通聊天机器人，而是一个执行型 AI 工作台：

```text
用户提出目标
→ Agent 理解任务
→ 选择模型和工具
→ 直接执行本地工作
→ 修改代码或文件
→ 运行验证
→ 失败时自动修复
→ 用最少文字交付结果
```

产品必须同时满足：

1. 处理速度快：减少无效模型调用、重复读取和冗余输出。
2. 成果质量高：修改必须可验证，不能只生成文字答案。
3. 回复简洁：用户主要看结果，不看 Agent 自我解释。
4. 可塑性强：模型、工具、Skill、Prompt、工作流都可替换。
5. 编码能力强：能理解真实仓库并完成多文件修改、测试和修复。
6. 界面简单：接近 Codex/Claude 工作台，不做复杂项目管理系统。

## 三、P0：执行内核

### 3.1 统一任务状态机

统一任务状态：

```text
queued
→ planning
→ running
→ waiting_approval
→ paused
→ resuming
→ verifying
→ completed / failed / cancelled
```

要求：

- 状态变化写入事件表。
- 每个任务有唯一 `task_id`、`run_id` 和 `trace_id`。
- Worker 重启后可以从最后安全节点恢复。
- 已执行成功的 ToolCall 不得重复执行。
- 任务取消后不得继续产生新的写操作。
- 前端可以区分运行中、等待授权、验证中和失败。

验收：

- 模拟 Worker 崩溃后，任务可以继续。
- 模拟 SSE 断开后，重新连接可以恢复完整状态。
- 同一个任务被两个 Worker 获取时，只允许一个执行。
- 取消任务后，不再修改文件。

### 3.2 执行闭环

实现并统一以下流程：

```text
读取目标文件
→ 搜索相关代码
→ 分析依赖
→ 生成最小修改
→ 应用修改
→ 查看 diff
→ 运行测试/lint/typecheck
→ 失败则修复
→ 再次验证
→ 交付摘要
```

要求：

- 修改前记录文件版本或可回滚快照。
- 修改后自动执行与项目匹配的验证命令。
- 验证命令从项目配置中识别，不硬编码单一命令。
- 支持 Python、Node、TypeScript、PowerShell、Shell 项目。
- 输出过长时保存为 Artifact，只在界面展示摘要。
- 每次工具调用记录输入、结果、耗时、状态和错误。

验收：

- 能完成至少一个多文件真实重构。
- 能识别测试失败的具体文件和错误原因。
- 能自动修复至少一次编译或测试错误。
- 失败时不破坏原有可运行状态。

### 3.3 安全执行

高风险行为必须进入授权流程：

- 删除文件或目录。
- 执行不可逆数据库操作。
- `git push`、强制覆盖、重置历史。
- 安装系统级依赖。
- 访问工作区外路径。
- 发送外部网络请求。
- 执行高风险 Shell/PowerShell 命令。

授权卡必须说明：

- 将执行什么。
- 影响哪些文件或资源。
- 是否可回滚。
- 不授权会怎样。

## 四、P0：模型路由和推理

### 4.1 模型注册中心

建立统一模型配置结构：

```json
{
  "id": "model-id",
  "provider": "provider-name",
  "endpoint": "https://...",
  "capabilities": ["text", "tools", "vision", "reasoning"],
  "contextWindow": 128000,
  "priority": 10,
  "enabled": true
}
```

要求：

- 支持多个供应商和多个模型。
- 用户可以新增、编辑、禁用模型。
- API Key 必须加密保存。
- 模型列表不能写死在前端。
- 模型不可用时显示真实错误。
- 切换模型后下一轮请求必须使用新模型。

### 4.2 智能路由规则

默认按照任务类型路由：

| 类型 | 路由倾向 |
|---|---|
| 简单问答 | 低延迟、低成本 |
| 快速改文件 | 工具调用稳定 |
| 大型重构 | 强推理、长上下文 |
| 测试修复 | 强推理、代码能力 |
| 文档生成 | 长上下文、语言质量 |
| 逆向分析 | 代码理解、长上下文 |
| 图片/截图分析 | 视觉模型 |

用户可以覆盖默认路由：

- 固定模型。
- 固定供应商。
- 速度优先。
- 质量优先。
- 成本优先。

验收：

- UI 可以切换模型。
- 后端收到的模型参数与 UI 一致。
- 失败模型能重试或切换备用模型。
- 路由决策写入事件日志。
- 不因为模型切换丢失当前任务上下文。

### 4.3 上下文优化

上下文分为：

```text
系统规则
→ 当前场景规则
→ 用户目标
→ 仓库摘要
→ 当前文件片段
→ 工具结果摘要
→ 历史任务摘要
```

要求：

- 文件按需读取，不发送整个仓库。
- 搜索结果支持分页和数量上限。
- 工具输出超过阈值后保存 Artifact。
- 相同文件和相同命令结果支持缓存。
- 长任务自动生成阶段摘要。
- 上下文压缩不得丢失用户目标、修改文件和失败原因。

## 五、P0：编码能力

### 5.1 必须具备的编码能力

- 全仓库搜索。
- 按符号、函数、类和引用定位代码。
- 多文件依赖分析。
- 前后端联动修改。
- 数据库迁移。
- 测试生成和测试修复。
- 类型错误修复。
- lint 修复。
- Git diff 审查。
- 文件回滚。

### 5.2 修改质量要求

每个修改任务必须检查：

- 是否修改了正确文件。
- 是否引入重复逻辑。
- 是否破坏已有 API。
- 是否修改了不相关文件。
- 是否缺少测试。
- 是否存在类型或格式问题。
- 是否存在跨平台问题。

验收：

- 建立至少 30 个真实编码 Benchmark。
- 记录成功率、一次通过率、平均耗时和返工次数。
- 每次内核改动自动跑 Benchmark。
- Benchmark 结果保存为 JSON，不能只看人工感觉。

## 七、P1：场景系统

### 7.1 默认场景

首版只保留以下场景：

1. 开发
2. 文档
3. 日常
4. 头脑风暴
5. 逆向实验室

场景不能只是名称变化，必须真正影响：

- 默认模型。
- 可用工具。
- 输出格式。
- 是否允许修改文件。
- 是否启用长期记忆。
- 默认输入提示。

### 7.2 日常场景

只有日常场景显示：

- 记住习惯。
- 不记住。

记住习惯时可以学习：

- 输出长度偏好。
- 常用工具。
- 常用工作流程。
- 常用文件位置。
- 常用语言和格式。

不记住时：

- 不写入长期记忆。
- 不更新 Skill。
- 任务结束后只保留必要运行记录。

验收：

- 开发场景不显示日常记忆开关。
- 切换到日常场景后显示记忆选择。
- 记忆可以查看、编辑和删除。
- 敏感信息不得自动学习。
- 日常记忆不能污染开发场景上下文。

## 八、P1：前端页面

### 8.1 页面结构

只保留四部分：

```text
左侧：新对话、历史对话、底部逆向实验室和设置
顶部：场景、模型、服务状态
中间：任务过程和结果
底部：输入框、附件、发送/停止
```

要求：

- 场景入口只保留顶部一个。
- 模型入口必须可操作，不能是静态文字。
- 设置只保留左下角一个入口。
- 逆向实验室只保留左下角一个入口。
- 删除重复的导航、项目入口和功能卡片。
- 默认首页不展示项目管理面板。
- 不展示大段产品宣传文字。
- 复杂信息放到详情抽屉或展开区域。
- 任务结果优先，过程信息默认折叠。

### 8.2 场景切换体验

切换场景时必须同步改变：

- 输入框提示词。
- 当前 Skill。
- 默认模型。
- 工具权限。
- 输出格式。
- 记忆开关。

切换过程中：

- 不丢失当前输入。
- 不误改当前任务。
- 当前对话显示使用的场景和模型。

### 8.3 回复展示

成功结果默认展示：

```text
已完成

修改：
- 文件 A
- 文件 B

验证：
- 测试通过
- 类型检查通过
```

详细日志、工具参数、完整 diff 放入可展开区域。

## 九、P1：性能目标

建立性能指标并持续记录：

| 指标 | 目标 |
|---|---:|
| 首页首次可交互 | ≤ 2 秒 |
| 新对话响应首字节 | ≤ 2 秒，受模型服务影响时显示等待状态 |
| 场景切换 | ≤ 300ms |
| 模型切换 | ≤ 300ms |
| 小文件搜索 | ≤ 500ms |
| 任务事件显示延迟 | ≤ 300ms |
| 普通任务无效模型调用 | 0 次 |
| 工具结果重复读取 | 尽量为 0 |

要求：

- 前端长列表虚拟化。
- SSE 只推送增量事件。
- 大文件和长输出使用 Artifact。
- API 查询必须分页。
- ToolCall、事件、Evidence 不允许无限 `.all()`。
- 记录模型耗时、工具耗时和数据库耗时。

## 十、P2：评测系统

建立四类评测：

### 编码评测

- 单文件修复。
- 多文件重构。
- API 修改。
- 前后端联动。

- 首次响应时间。
- 总任务耗时。
- Token 消耗。
- 工具调用次数。
- 失败重试次数。

每次升级必须输出：

- 总任务数。
- 成功数。
- 失败数。

- 测试通过率。
