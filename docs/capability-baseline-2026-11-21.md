## 二、成本结构

- **缓存命中率 86%–95%**：prompt token 的绝对数很大，但绝大部分命中供应商缓存；
  真正按全价计费的增量只有 5%–14%。
- **活跃上下文不大**：T01 的 `context.breakdown` 是工具说明 22,626 字符、
  消息 13,558 字符，合计约 36k 字符（~9k tokens）；prompt 累计到 134k 是因为
  7 次调用各重发一次，不是上下文真的涨到 134k。
- **成本主要由调用次数驱动**：T09 19 次调用、T07 9 次、T01 7 次。优化方向应是
  “减少不必要的往返”，而不是继续压上下文长度。

## 三、当前结论

1. 五个样例全部通过，编程/文档/数据的小任务能力可用；验收覆盖在 C3 后为 1.0。
2. 上下文不是当前的瓶颈；调用次数才是。下一步若要省钱，应先查 T09 这类任务
   为什么需要 19 次调用，而不是继续改压缩阈值。
3. 小样例通过不等于大任务能做完。原 shopbench 任务 `a69c01d2` 曾在
   `write_file` 10706 字符截断处失败；当前代码已有恢复路径，正在独立临时工作区复跑，
   结果另记。

## 四、真实任务复跑（shopbench）

- 复跑任务 `7ce98397`：**succeeded，27 步**，产出 11 个文件（服务端、模拟器、
  本地规则引擎、前端 5 个视图），`npm test` 18 项通过。
- 但交付文本自己写着：「前端导航点击无反应，五个视图进不去」「需要你：…重跑」。
  这说明两件事：
  1. 大文件截断恢复已经生效，原 `a69c01d2` 的 10706 字符失败没有重演；
  2. 交付不完整仍被判 succeeded——C1 的未完成词表漏了「无反应 / 进不去 / 重跑」，
     已在本轮补上并用该交付文本加了判据。
- 随后创建修复任务 `37032c7b`，要求 Agent 自己修 `switchView` 的
  `history.replaceState` 并用 `browser_check` 点完五个导航项：
  - 结果 **succeeded，32 步**，只改 `public/app.js` 一处；交付称六个视图可切换、
    HTTP 下控制台零错误。
  - 用仓库自带的 `browser_probe.mjs` 独立复核：
    - `file://` 打开：16 条导航/独占断言全过，但 14 条控制台错误全部来自
      `file://` 下 fetch `/api/*` 的 CORS（页面需要自己的服务端）；
    - `http://127.0.0.1:4173` 打开：**16/16 断言全过，0 控制台错误，0 失败请求**，
      商品数据正常加载。
  - 结论：导航修复有效；这个交付的正确打开方式是 `node server.js`（默认 3000，
    与主应用冲突，实测用 `PORT=4173`），不是双击 `index.html`。
- 交付文本里仍有「需要你：…跑一次…确认」，这是本次真实任务留下的最后一个
  非自主项：Agent 自己已经用 browser_check 验过 HTTP 模式，但把 file:// 的
  复核交回用户。C1 的词表已覆盖「无反应/进不去/重跑」，这次没有覆盖「跑一次」；
  是否把「跑一次」也列为阻塞，留待下一轮定（本轮先记录事实，不扩大改动）。

## 五、边界

- 只跑了一个供应商（DeepSeek flash）；不同模型的失败形态不同。
- 样例都是仓库自带的小任务，不代表大型多文件项目。
- `acceptance_coverage` 只数 `covered=true`；未判定单列，不算覆盖。
- 评测产生的临时项目与工作区已清理；原始结果文件在 `evals/results/`。

## 六、harness 生成质量闸门（D2，2026-11-21）

- 前端改动现在有机器闸门：最后一次前端写入之后必须有 `browser_check` 回执，
  且控制台 0 错误、0 失败请求、至少 1 条通过的断言和 1 条通过的动作；否则验证失败，
  自动回执行节点，并注入「打开 → 断言 → 动作 → 零错误」的修复指令。
- 真机验证：
  - `5a814453`：从零做计数页，7 步 succeeded；browser_check 带 3 条断言与
    多个点击/断言动作，控制台 0 错误。
  - `c0ceba72`：在现有页面加说明，7 步 succeeded；交付文本显示
    「已做浏览器自检（browser_check 通过：…1 个断言 / 6 个动作）」，
    事件 `ui.check_passed` 落盘；不再只剩「未跑校验」。
  - `f31d0504`：修复前三个并行 browser_check 触发 400
    （`insufficient tool messages following tool_calls`）；定位为带图 user 消息插在
    tool 消息之间，已改为整批 tool 消息写完后再追加截图，后续任务未再复现。
- 闸门不把环境问题算成页面缺陷：没有 node/Chrome/探针时记 `ui_check=unavailable`。
- 这一层修的是"生成后怎么被拦住"；提示词里的反 AI 与安全底线仍是第一道，审查清单
  是第二道，浏览器证据是第三道。
