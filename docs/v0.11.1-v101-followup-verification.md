## 2. §2 后端自动执行：不卡了，但诊断缺失

`tests/test_backend_autostart_v101.py` 加 `timeout 240` 复现：`10 passed / 15.96s / EXIT=0`。
核心用例确实断言了 `run.created / run.started / task.auto_started(source=backend)`，
不是靠 mock 敷衍。任务单描述的「长时间不结束」在 v0.11.1 上**不再复现**，历史卡住的
根因无从反推（当时没有留诊断），不编造解释。

真正缺的是 §2.3：`_wait_terminal` 超时只留一句「任务没有跑完」。已改为

- 超时 `pytest.fail()`，**带着诊断失败**，不再无限等、也不静默返回；
- 一次打全 task_id / goal_id / run_id / task.status / run.status / dispatch.auto_start /
  dispatch.decision / provider_id / run.worker_id / run.attempts / run.lease_expires_at /
  run.last_beat（= `updated_at`）/ 最近 20 条 AgentEvent；
- 没有 run 行时同样显式写 `run.status=（无）`，不让人猜是漏打还是没建。

诊断函数平时不执行，属于「真出事时才发现它坏了」的代码，所以补了 2 个自测
（`test_backend_autostart_diagnostics_v101.py`），**单独放一个文件**，让原文件仍是
任务单要求的严格 10 例。

## 3. §3 审批链路：查出并修掉两个真缺陷

### 3.1 现有测试为什么全绿却漏了

`test_approval_identity_v101.py`（9 例）、`test_approval_card_v101.py`（40 例）覆盖的是
**主循环审批门**（`_approval_gate`）。真机上弹出的那张卡走的是另一条路：
`run_validation_node → _ask_run_tests_approval`（`source=validation`）。它生成的
`approval.required` 里只有 `tool / approval_key / permission_* / expires_at / source`，
`approval_id / tool_call_id / tool_name / arguments_hash / resource_path` **一个都没有**。

后果不只是「少几个字段」：`_decide_approval_locked` 的精确匹配被
`if provided and identity` 整段跳过，退回「任务当前在等的那张卡」——正是 §3.2
明令禁止的按第一条 pending 猜。同时这条通道把 TTL 写死 5 分钟，主循环早已改成
可配的 30 分钟（同一个界面上两张卡寿命不同，人离开一会儿点下去就是 409）。

真机抓到的旧卡（修复前）：

```
approval.required  keys = approval_key, approval_options, arguments, expires_at,
                          permission_mode, permission_rule, risk_level, source, tool, trace_id
pending_approvals  approval_id / tool_call_id / arguments_hash / resource_path 全空
```

### 3.2 修了什么

| 位置 | 改动 |
|---|---|
| `graph.py::_ask_run_tests_approval` | 与主循环同源的 `approval_identity()`；TTL 改用 `approval_ttl_seconds()`；`approval.granted / denied` 都带身份；返回身份给调用方 |
| `graph.py::run_validation_node` | 批准后发 `tool.requested`（前端按它与 `tool.completed` 配对），`tool.completed` 带同一组身份；驳回时一条执行事件都不发 |
| `graph.py::approval_identity` | 补 `tool_name` 别名（历史代码用 `tool`，任务单要求四元里有 `tool_name`） |
| `graph.py::_call_identity` | `tool.requested / tool.completed` 主循环两处也带身份，审计能把「批了」和「跑了」按 `approval_id` 对上 |
| `tasks.py::_decide_approval_locked` | 四元匹配真正加进 `provided`；`approval.decided` 记全 `tool / tool_name`；老事件没有 `tool_name` 时用 `tool` 补齐，不让老卡批不动 |
| `schemas/task.py` | `TaskApprovalIn` 新增 `tool_name` |
| `evidence.py` | 待审批卡带 `tool_name` |
| 前端 4 个文件 | 卡片 normalize 出 `toolName`，三处 `decideApproval` 调用把它发出去 |

**`tool.started` 的口径**：任务单 §3.4 写 `tool.started`，本仓库的开始半事件叫
`tool.requested`（`turns.ts` 就是按 `tool.requested / tool.started` → `tool.completed`
配对的）。**没有**另造一个 `tool.started`：那样前端会多出一条永远停在 running、
配不上结束事件的卡片。事件链语义齐全，只是名字不同，这里如实说明，不假装改名了。

### 3.3 真机又抓到第二个缺陷：恢复后身份断成两截

第一次修完、热同步进安装版后点了一次「仅本次允许」，事件链是：

```
41 approval.required   apr-31648be176f9070c   call=validation:83c45791-…（AgentRun UUID）
44 approval.decided    apr-31648be176f9070c
48 approval.granted    apr-ca6c50259490c4bd   call=validation:task:…:attempt:1
49 tool.requested      apr-ca6c50259490c4bd
50 tool.completed      apr-ca6c50259490c4bd
```

`run_id` 在中断前是 `AgentRun.id`（UUID），审批恢复后 runtime 传的是
`task:<id>:attempt:1`。我拿它当定址键，于是同一张卡批前批后两个 id。改成
**跨中断恒定的 `trace_id`**（`task:…:attempt:N`，重试换 attempt 又会变），并补两条
单测：`test_identity_survives_the_approval_resume` / `test_a_new_attempt_generates_a_new_approval`。

## 11. 未完成 / 已知限制 / 阻塞

**未完成（未验证）**

1. `Clipboard_Screenshot.png` 授权后真实读取：本机 4 个供应商全部 `supports_vision=False`，
   没有可看图的模型；附件上传与「不支持看图」的如实提示已验，图片读取未发生。
2. 自动修复「失败→修→再测」真机闭环：只有代码路径与单测，没有做过带真实编译/测试失败的任务。
3. 审批档在免打扰时段照响、防刷屏 1 分钟 3 条上限：只有单测/接口层，未做真机。
4. 设置页「通知与免打扰」面板外观：只过了 tsc / lint / 接口，未截图验收。

**已知限制**

- `tool.started` 在本仓库叫 `tool.requested`；前端按它配对结束事件，另加同名事件会造成
  永远 running 的重复卡片。语义对齐，名字未改。
- `run_tests` 的 `resource_path` 为空串（参数 `{}` 本来就没有资源路径），卡上是 `null`，
  这是如实值，不是漏字段。
- 老中断事件（v0.11.1 之前）没有身份；审批 API 保持「不带身份就不校验」的兼容行为，
  不会让存量待审批任务突然点不动。
- 本轮是源码级修复：安装版通过 `self-deploy.cjs --api/--web` 热同步后重启用于验收，
  **没有重新打安装包**；`dist/Blank-AI-安装版-0.11.1.exe` 仍是修复前的产物。

**阻塞问题**

- 缺一个 `supports_vision=True` 的供应商，否则 §3.5 无法闭环；这是任务单 §10 明列的
  「Clipboard_Screenshot 未真实验证」，因此**不报告「全部完成」**。
