# UI 参考调研：opencode 与 DeepSeek（2026-11-19）

取证方式：官网静帧/视频封面（webp 转 png）、GitHub 主题源码、Apple App Store 官方截图（iTunes lookup API）、GIGAZINE 与官网实机图、无头 Chrome 渲染截图。图片全部落在 `D:/kbg harness/_shots/external/`，逐张来源见第六节。

先纠正两个前提，后面的判断都建立在这上面：

1. **opencode 的 TUI 现在不是 Go 写的。** 仓库 `anomalyco/opencode` 的 `packages/tui` 已是 TypeScript（`bunfig.toml` + `src/*.tsx`，Bun 运行），早期 0.x 才是 Go。语言换了，但终端里的**行结构、配色、审批块形态没有变**，仍然可以按截图抄。
2. **DeepSeek 不是没有 coding 产品。** 官方 coding agent 叫 **DeepSeek Harness**：2026-08 发 0.1，2026-10-01 发 0.2 并上线 macOS / Windows 桌面端（`deepseek.com/harness`）。它的桌面界面比 chat 更值得我们看，而且和我们是同一类产品（会话 + 步骤 + 工具 + diff + 产物预览）。

---

## 一、一句话结论

**最值得抄的是 DeepSeek Harness 的「双密度」结构：同一个任务，对话视图 13px/1.7 只讲人话，轨迹视图 11px 等宽、24px 行高讲全量事件，右栏 360px 只放产物与改动。**

单点最值得抄的是 opencode 的**「一次连续工具调用 = 一条可折叠活动行」**（`Used 1 Read`）。我们现在的每一步都是一张带边框的卡，这是视觉噪音的根源，不是配色问题。

两家都不把「步骤」做成卡片墙；我们把 12 次工具调用渲染成 12 张卡，方向是反的。

## 二、opencode

### 2.1 opencode：三种形态，三种信息架构

| 形态 | 会话列表在哪 | 主区 | 右栏 | 备注 |
|---|---|---|---|---|
| Desktop（Electron） | **顶部 tab**；v2.3.0 才加实验性 Recent 侧栏（7 天/30 条，可隐藏） | 单栏会话流 | 可切：diff / 内置浏览器 / 文件预览 | 官方主视觉是深色 |
| Terminal（TUI） | 不常驻，`/sessions` 或 `ctrl+o` 弹层 | 单列 transcript | 无 | 跟随终端明暗（v2.2.7 起） |
| Mobile | 列表页 | 会话 + 审批 | 无 | 主打「在手机上批准」 |

关键结论：**桌面端不是「左列表 + 右详情」的 master-detail，而是「多 tab + 单栏会话 + 可切右栏」。** 并行会话靠 tab，不靠列表。我们现在的 272px 左栏 + 中间时间线 + 384px 右栏，是把「浏览」和「执行」放在同一层级；他们把「切换会话」降级成 tab，把横向空间全给了对话与产物。

### 2.2 桌面端骨架

```
┌ macOS 窗口 ─────────────────────────────────────────────────────┐
│  [会话 A] [会话 B ●] [会话 C]                        标签栏 36px │
├──────────────────────────────────────────┬──────────────────────┤
│ 仓库名 / 会话标题            …   2k  ⧉   │  右栏（可折叠）       │
│                                          │  ┌────────────────┐  │
│                 ┌──────────────────────┐ │  │ diff            │  │
│                 │ 用户消息（右对齐）    │ │  │ 或内置浏览器     │  │
│                 └──────────────────────┘ │  │ 或文件预览       │  │
│                                          │  └────────────────┘  │
│  Used 1 Read              ← 活动行 24px   │                      │
│                                          │                      │
│  Pulled 12 facts from notes/trip.md...   │                      │
│  正文 13px / 行高 1.65                    │                      │
│                                          │                      │
│                 ┌──────────────────────┐ │                      │
│                 │ 第二条用户消息        │ │                      │
│                 └──────────────────────┘ │                      │
│  Working                 ← 12px 灰字      │                      │
│                                          │                      │
│  ┌────────────────────────────────────┐  │                      │
│  │ Ask anything, / for commands, @... │  │                      │
│  │ +   Claude Opus 5.5 ˅         ↑    │  │                      │
│  └────────────────────────────────────┘  │                      │
└──────────────────────────────────────────┴──────────────────────┘
```

会话页从上到下只有 5 种东西：**用户气泡、助手正文、活动行、diff 块、状态行**。没有「步骤卡」「工具卡」「系统卡」的区分。

### 2.3 信息层级：一次运行 = 一行

- 用户消息：右对齐灰气泡（取色 `#2f2f2f`），圆角约 16px，内边距约 10×14，最大宽度约会话列的 75%。
- 助手正文：**没有气泡、没有边框**，直接铺在画布上，13px。
- 连续的工具调用和思考：合并成一条**活动行**，例如 `Used 1 Read`。数字加粗，动词灰色，行高约 24px，右侧一个 12px 的 chevron。
- 展开后才是工程细节：工具名、参数、输出，12px 等宽，单行截断。
- diff 直接出现在时间线里（不是跳到另一个页面），带行号、`+1 -0` 头和绿色/红色行底。
- 没有「完成卡片」；运行中只多一行 `Working`，没有勾选徽章。

这一条有官方 changelog 佐证（v2.3.0，2026-11-13）：

> "The TUI now summarizes each run of tool calls and thoughts into one collapsible activity row, so the answer is easier to follow. To see every step again, set Verbosity to `medium` or `high`."

所以它是**默认安静、按需展开**，而不是「默认全量、用筛选器减法」。我们的 7 个筛选 chip（全部/计划/工具调用/终端/提问/审批/结果，`task-console.tsx:36`）本质是在补偿「默认太吵」。

### 2.4 状态怎么表达

| 状态 | 视觉 | 位置 |
|---|---|---|
| 运行中 | 纯文字 `Working`，12px，`#808080`，不加底色、不加边框 | transcript 末尾 |
| 某个工具完成 | `Used 1 Read`，12px，数字加粗 | 该段活动行 |
| 上下文用量 | `2k`，11px 等宽，`#808080` | 会话头右侧 |
| 代码变更 | `+1 -0`，绿/红，11px 等宽 | diff 块头部 |
| 失败 | 只有这一块左侧 2px 红条 + 输出红字；页面顶部不弹全局错误条 | 原地 |
| 等待审批 | 一个占满宽度的阻塞块插在时间线里（见 2.5） | 当前流的下一条 |

要点：**状态是句子，不是徽章。** 他们没有 `StatusBadge` 这种带底色和描边的组件，颜色只出现在「真的出错」和「diff 增删」上。

### 2.5 审批提示：插在时间线里的阻塞块

TUI 的形态（官方 feature 视频静帧，见 `opencode-tui-permission.png`）：

```
┌──────────────────────────────────────────────────────────────┐
│ ⚠ Permission required                                        │
│                                                              │
│ $ bun test                                                   │
│                                                              │
│ [Allow once]   Always allow   Reject          ctrl+f full…   │
└──────────────────────────────────────────────────────────────┘
```

- 位置：紧接在触发它的工具块之后，**占满 transcript 宽度**，不弹模态框、不盖住对话。
- 标题：`⚠ Permission required`，警告黄；命令单独一行，12px 等宽，前缀 `$`。
- 选项：`Allow once`（默认焦点，深蓝灰填充选中态）、`Always allow`、`Reject`。拒绝会同时拒掉该会话内所有待审批请求（官方 Permissions 文档明确写了这一点）。
- 右侧是 `ctrl+f full…` 这类快捷键提示，11px 灰。
- 子代理的审批会出现在你正在看的子会话里，也会显示在已打开的 composer 前面（v2.3.1 changelog）。

桌面端的审批态没有拿到可信截图（官网产品图里没有），这里不臆测；能确认的是同一套 `Allow once / Allow always / Reject` 语义。

### 2.6 字体、字号、间距

TUI 没有「字号」，只有终端网格。它的层级靠**缩进、左侧竖线、底色、前景色**，不靠字号——这是它看起来比同信息量的 Web 界面安静的原因。

桌面端按 1200×750 官方静帧折算（原图可能是 1.5× 导出，数值有 ±1px 误差）：

| 元素 | 字号 | 行高 | 字重 |
|---|---|---|---|
| 会话标题（头部） | 14px | 1.4 | 500–600 |
| 正文 | 13px | 1.65 | 400 |
| 活动行 | 12px | 1.5 | 数字 600，其余 400 |
| 元信息 / 计数 / 时间 | 11px | 1.4 | 400，等宽 |
| 代码 / diff | 12px | 1.55 | 等宽 |
| 用户气泡 | 13px | 1.6 | 400 |

间距：气泡内边距 10×14；正文段间距 12px；消息之间 20–24px；活动行上下各 4px；composer 高约 88px（两行），圆角 12px；右栏与主区之间没有 1px 分隔线，靠 `#141414` 与 `#0a0a0a` 的底色差分开。

### 2.7 配色（可读到具体值）

来自 `packages/tui/src/theme/assets/opencode.json`（TUI 主题），以及桌面截图像素取样：

| 用途 | 深色 | 浅色 |
|---|---|---|
| 画布 | `#0a0a0a` | `#ffffff` |
| 面板 / 卡片 | `#141414` | `#fafafa` |
| 边框（弱/强） | `#1e1e1e` / `#282828` | `#ebebeb` / `#e1e1e1` |
| 正文 | `#eeeeee` | `#1a1a1a` |
| 次要文字 | `#808080` | `#8a8a8a` |
| 主色（强调） | `#fab283`（暖橙） | `#3b7dd8`（蓝） |
| 成功 | `#7fd88f` | `#3d9a57` |
| 警告 | `#f5a742` | `#d68c27` |

注意：主色是**暖橙**，不是蓝；而且只出现在光标、选中项、少量链接上。diff 与环境色（蓝/紫）都是语义色，不参与品牌表达。整个界面 90% 的像素只有 4 个灰阶。

## 三、DeepSeek

### 3.1 产品面：Harness 才是对标物

| 产品 | 形态 | 有没有 coding 界面 |
|---|---|---|
| DeepSeek App / chat.deepseek.com | 手机 App + 网页对话 | 没有代码文件、diff、工具步骤 |
| **DeepSeek Harness** | macOS/Windows 桌面端 + Web + CLI | **有，而且就是 coding agent** |
| API 平台 | 控制台 | 无对话界面 |

`chat.deepseek.com` 未登录会直接跳手机号/微信扫码登录（见 `deepseek-chat-login.png`），所以网页对话的实机截图没拿到；App 的官方截图来自 App Store，能覆盖「长回答 / 思考过程 / 输入框」，但**没有一张代码块截图**，代码块样式不臆测。

实测尺寸（1200px 宽实机图，1× 折算）：侧栏 250px；主区约 860px；右栏在 review 图里约占一半宽度（窄聊天列 + 宽 diff 列）；会话正文行宽约 620px。窗口整体 `#151515`，侧栏带 macOS vibrancy（半透明，叠在壁纸上取样为 `#333c4a` 一带），主区与侧栏之间**没有分隔线**。

### 3.3 会话页信息层级

从上到下只有 4 层，比 opencode 还少：

1. **用户气泡**：右对齐，`#2b2b2d`，圆角 16px，13px。
2. **思考行**：`已思考（用时 90 秒）›` 或英文 `Thought for a while ›`，12px 灰，默认折叠成一行。展开后才是推理条目。
3. **正文**：13px，段距 12–14px，只有 `1. 2. 3.` 列表和加粗小标题，没有卡片。
4. **产物**：文件卡一行 40px（图标 + 文件名 + `+1 -8` + hover 才出现的操作），点击在右栏预览；没有单独的「交付区」。

另外，据实机评测（JOTO，2026-09-25，第三方，未独立验证）：回答区顶部会先给一条任务回执，形如「处理完成 / 执行完成」，后面跟上下文 token 数、工具调用次数、耗时。这条如果属实，正好补上「完成态说什么」。

同一篇评测的截图里还看到**三档工作过程展示偏好**：`聚焦结果` / `关键细节` / `完整过程`。这解释了为什么默认视图可以这么安静——吵的那部分被做成用户可选项，不是默认。

### 3.4 核心：Chat 与 Trajectory 是两种密度

会话头只有两个 tab：`Chat`（蓝色下划线，2px）与 `Trajectory`。同一个任务：

| 维度 | Chat | Trajectory |
|---|---|---|
| 字号 | 13px | 10–11px 等宽 |
| 行高 | 22–25px（约 1.7–1.9） | 23–24px |
| 内容 | 自然语言、文件卡、diff 摘要 | 每一轮、每个 cell 的原文 |
| 列 | 无 | Turn / 类型 / 内容 / 时间 |
| 颜色 | 黑灰 + 品牌蓝 | 5 种类型色标签 |
| 右栏 | 无 | 360px 检查器 |

轨迹表的实际结构（`deepseek-harness-trace.png`）：

```
┌ 对话 | 轨迹 ─────────────────────────────────────────────────────────────┐
│ ▶ Duration  ▌T Turns  ▤ Cells  ↓ Export              [搜索…]             │
│ Input ███▓▓▓▒▒▒░░░  ← 一条按 token 占比着色的事件密度条                   │
├────────┬──────────┬──────────────────────────────────┬───────────────────┤
│ Turn 1 │ SYSTEM   │ Initial System Prompt            │ TOOL · Turn 3     │
│        │ USER     │ 你好，请介绍一下你自己             │ Summary|Payload|  │
│        │ CONTEXT  │ Current runtime context...       │ Result|Schema|    │
│        │ ASSISTANT│ 你好！很高兴认识你...              │ Timing            │
│        │ TOOL     │ bash {"command":"pwd && ls -la"} │                   │
│ Turn 2 │ ...      │ ...                              │ Status: Completed │
├────────┴──────────┴──────────────────────────────────┴───────────────────┤
│            任务 1 进行中 · 4 待处理  ⌃⌄                                  │
└──────────────────────────────────────────────────────────────────────────┘
```

- 类型标签：`SYSTEM` 深灰蓝、`USER` 蓝、`CONTEXT` 紫、`ASSISTANT` 绿、`TOOL` 橙；9px 大写等宽、白字、圆角 3px、内边距 1×5。
- 每行只显示一行内容，超出截断；不做多行卡片。
- 右侧检查器五个 tab：`Summary / Payload / Result / Schema / Timing`，全部 10px 等宽、键值对排列，像 DevTools 而不是像文档。
- 左侧 `Input` 密度条：把上下文按段落类型着色，宽度即占比。这是「一眼看到 token 花在哪」的组件，比我们的字符账单直观。

**这套东西的说服力在于：它没有增加信息，只是把同一份信息换了一种密度和容器。** 我们的 `boundary`、`context.breakdown`、`JSON 参数`、`refs` 全部塞在时间线的卡片里，等于把 DevTools 混进了聊天流。

### 3.6 DeepSeek App / 网页对话：极简聊天长什么样

官方 App Store 截图（v2.8.0，2026-11-12）能确认的部分：

- 首页是一整片白：左上圆形菜单、右上圆形加号，中间蓝色鲸鱼 logo + 一句 `下午好，有什么可以帮到你？`（约 17–18px，500 字重）。
- 输入框是**一张白色圆角卡**（圆角约 24px，1px 浅灰描边 + 极轻阴影），浮在页面底部，不是贴边的横条。占位文字 `发消息或按住说话`，14–15px 灰。
- 卡内第二行左侧两个描边胶囊：`深度思考`、`智能搜索`；激活态浅蓝底 + 品牌蓝文字，未激活白底 + 灰描边。右侧是加号与语音。
- 输入框下面还有一排入口卡：`拍照 / 相册 / 文件`，浅灰底、圆角 12px、图标 + 12px 标签。
- 长回答：没有气泡，直接正文；小标题加粗（`理解问题`、`第一部：《三体》`），正文约 15–16px、行高约 1.7，段距 14–16px；公式居中、上下留白 20px 以上。
- 思考过程：
  - 展开态：`正在思考 ˅`（12–13px 灰）下面是一串带圆点的条目；工具动作用一行小字 + favicon 组表示，例如 `已搜索到 17 个网页` 后面跟 3 个 Google favicon、`已浏览 3 个页面` 后面跟 3 个站点图标、`查找关键词` 带文档图标。
  - 折叠态：`已思考（用时 90 秒）›`，**一整段推理只占一行**，紧接着就是答案的第一句（`答案：最小的正整数是50。` 加粗）。
- 输入框始终固定在底部，上方用白色渐变遮住滚动内容；状态只出现在消息流里，输入区不承担状态播报。

一句话：DeepSeek 把「过程」做成可折叠的**次要信息**，把「答案」做成唯一的视觉主体。我们现在的做法正相反——过程是主体，答案只是最后一张卡。

## 四、对照我们

现状（`web/src/app/globals.css`、`tasks-view.tsx:427`、`timeline-blocks.tsx:79`）：

- 骨架：`272px 任务列表 | 1fr 时间线 | 384px 右栏`，gap 12，xl 以下塌成一列。**这个三栏骨架本身没问题，和 Harness 的 review 场景几乎一样。**
- 时间线：每个事件一张卡。`CardShell` 用 `rounded-xl border px-3.5 py-3`，卡间距 10px。工具卡默认折叠，但**仍然是卡**，头部还有状态、风险、边界三个 chip。
- 顶部：标题 + StatusBadge + LiveBadge + 事件数 + 7 个筛选 chip，一行里出现 5 种信息、3–4 种颜色。
- 字号：正文 13、辅助 11–12、标题 13–15；浅色默认，窗口 `#e6e6e6`、画布 `#fff`、侧栏 `#f6f6f6`。

| 维度 | 我们 | opencode / Harness | 结论 |
|---|---|---|---|
| 会话切换 | 272px 常驻列表 | tab；列表降级为可选侧栏 | 我们横向空间被列表吃掉；但任务型产品需要列表，保留，压到 240px |
| 一步的容器 | 一张 60–110px 的卡 | 一条 24px 的活动行 / 一行 mono | **差距最大**，12 步就是 900–1200px vs 72px |
| 工程细节 | 风险/边界/JSON/refs 在卡里 | 默认全折叠，轨迹视图另开 | 我们把 DevTools 混进了正文 |
| 状态 | 带底色的徽章 + 脉冲点 | 一句 12px 灰字 | 徽章把「状态」提升成了「内容」 |
| 失败 | 整卡泛红（描边 + 浅红底） | 只红这一行/这一块 | 我们过度告警 |
| 颜色 | brand + ok + warn + danger 同时出现 | 90% 灰阶，1 个强调色 | 我们的颜色在抢注意力 |
| 深浅 | 浅色默认 | 深色默认（Harness / opencode 主视觉） | 不是必须跟，但深色更适合长时间盯 |
| 交付 | 结果卡 + 右栏文件/改动/证据/终端 4 个 tab | 文件卡一行 + 右栏预览 | 我们的右栏其实是对的，缺的是「对话区只留一行」 |
| 证据链 | 有 boundary/context/refs，可审计 | 轨迹视图 + 检查器 | 我们的数据更全，但表达更吵 |

他们比我们好的地方：**压缩、克制、双密度、把「过程」降级为可选**。

我们比他们好的地方，别抄丢了：

- 审批与提问的闭环更完整（同意/拒绝 + scope + 问题选项），opencode 只有三按钮，Harness 的审批态没看到。
- 中文工具描述已经写成人话（`describeTool`），比 `Used 1 Read` 更有信息量；问题只是容器太重。
- 证据链（窗口链、压缩前后、替换记录）比他们的 trace 更可审计，这是差异化，不该为了「简洁」删掉，应该搬进右栏。
- 失败态有明确的危险色语义，适合企业场景；只要缩小到行级即可。

## 五、可以直接照搬的 5 条

### 5.1 把「连续工具调用」合并成一条活动行

```
▸ 读了 1 个文件 · 跑了 2 条命令 · 用了 12s                     ⌄
```

- 触发：`buildBlocks` 后做一次 group pass，把**相邻同类**的 tool/terminal 事件合成一个 `activity` block；遇到 approval / question / result / 用户消息就断开。
- 行高 24px，上下 margin 4px；左侧 12px chevron；主文 13px/1.5 `#3f3f46`；计数用 11px 等宽 `#8b8b8f`；右侧耗时 11px 等宽。
- 默认折叠。展开后不是卡片，是**无边框列表**：12px 等宽、行高 22px、左侧 1px `#e4e4e4` 竖线（x=6px），每条一行，超长截断，hover 才显示「查看输出」。
- 超过 5 条折叠为 `+7 条`；不要一次展开 20 条。
- 预期：一次 12 次工具调用的任务，时间线从 900–1200px 降到约 200px。

落地：`web/src/components/tasks/timeline.ts` 加 group；`timeline-blocks.tsx` 加 `ActivityBlock`；`ToolCard` 保留给「失败」和「审批相关」的单条。

### 5.2 会话页加「对话 / 轨迹」两个 tab，右栏做检查器

- 顶部 tab 栏 32px 高，两个 tab，13px；激活态 2px `#1f1f1f` 下划线（深色皮肤用 `#ededed`），未激活 `#8b8b8f`。
- 对话：单列 `max-width: 760px`，正文 13px/1.65，段距 12px；只有用户气泡、助手正文、活动行、文件卡、审批卡五种东西。
- 轨迹：表格，行高 24px，11px 等宽；列宽 `48px Turn | 80px 类型 | 1fr 内容 | 56px 时间`；表头 10px 大写 `#8b8b8f`；类型标签 9px、内边距 1×5、圆角 3px、5 种低饱和底色（灰蓝/蓝/紫/绿/橙），白字。
- 右栏固定 360px（我们现有 384px，改成 360px 即可），tab 改为 `产物 / 改动 / 详情`；`boundary`、`context`、`refs`、原始 JSON 全部搬进「详情」，从对话流里消失。
- 交付：对话区只留一行 40px 的文件卡（图标 16px + 文件名 12px 等宽 + `+1 -8` + hover 操作），点击在右栏预览；最多 3 行，其余折叠成 `还有 4 个文件`。

预期：默认视图的信息密度接近 opencode，但完整数据一条不少。

### 5.3 状态从「徽章」降级为「一行字」

| 状态 | 文案 | 视觉 |
|---|---|---|
| 运行 | `正在执行 · 12s` | 6px 蓝点 + 12px `#5a5a5d`，无底色 |
| 思考 | `正在思考 · 4s` | 同上，点做 1.2s 呼吸 |
| 等审批 | `等待你确认 · 2 项` | 12px `#a16207`，左侧 2px 竖条 |
| 完成 | `完成 · 12 步 · 38s · 12.4k tokens` | 6px 绿点 + 12px `#15803d` |
| 失败 | `失败于「运行测试」 · 查看输出` | 6px 红点 + 12px `#b42318` |

- 位置：永远在消息流最后一行，不放进 header。
- header 只留：标题 15px/600 + 一个 6px 状态点 + 事件数 11px 灰。去掉 StatusBadge、LiveBadge 的底色和描边。
- 失败不整卡变红：只给该活动行左侧 2px `#b42318`，输出文字变红。
- 顶部不要同时出现 ok / warn / danger 三种语义色；同屏最多 1 个强调色。

### 5.4 审批卡做成三段式，固定在时间线里

```
┌────────────────────────────────────────────────────────────┐
│▌ 需要你确认：运行命令                          还有 2 个待确认 │
│                                                            │
│  $ bun test                                                │
│  ────────────────────────────────────────────────────────  │
│                              Enter 允许 · Esc 拒绝          │
│                            [拒绝]  [总是允许]  [允许一次]     │
└────────────────────────────────────────────────────────────┘
```

- 宽度占满时间线（max 760px），内边距 12×14，圆角 10px，边框 `#e2e2e2`，白底，**无阴影**。
- 左侧 2px 竖条：审批 `#a16207`，危险操作 `#b42318`。
- 标题 13px/600；命令块 12px 等宽、`#f6f7f9` 底、内边距 8×10、圆角 6px、最大高 120px 可滚。
- 按钮高 32px、13px、圆角 6px、间距 8px；主按钮 `#1f1f1f` 白字，次按钮白底 + `#d4d4d4` 描边，`拒绝` 用幽灵按钮 + `#b42318` 文字，放最左，和两个允许拉开距离。
- 快捷键提示 11px `#8b8b8f` 右对齐，放在按钮上方一行；不要用 modal，不要遮住上下文。
- 队列感：标题右侧 `还有 N 个待确认`，让用户知道批完还有。

### 5.5 统一一套「4 级字号 + 3 档间距」，并把深色底改成两档灰

| 层级 | 字号/行高 | 字重 | 用途 |
|---|---|---|---|
| L1 页面标题 | 15px / 1.4 | 600 | 任务标题、会话标题 |
| L2 正文 | 13px / 1.65 | 400 | 助手回答、审批标题 |
| L3 元信息 | 11px / 1.4 | 400 | 时间、耗时、token、状态句 |
| L4 等宽细节 | 11px / 1.5 | 400，等宽 | 轨迹表、chips、文件路径 |

- 间距只用 3 档：`8px`（行内/卡片内元素）、`12px`（卡片之间/段落之间）、`20px`（区块之间）。取消现在的 10px 这种中间值。
- 卡片内边距从 `14×12` 降到 `10×12`；圆角从 12px 降到 10px（审批/交付）/ 8px（普通行）；普通事件行**去掉边框**，只留左侧 1px 引导线。
- 深色不要把 `#0f0f11` 和 `#1a1a1d` 同时用在每个卡上：画布 `#151515`、面板 `#1b1c20`、hover `#212226`、线 `#26272b`，**用底色差代替 1px 边框**（这是 Harness 和 opencode 共同的做法）。
- 浅色保持现有 `#fff` 画布，但把窗口底 `#e6e6e6` 提到 `#f2f2f3`，减少「灰框套白框」的层数。
- 品牌近黑 `#1f1f1f` 继续用于主按钮；新增一个 `--run: #3964fe` 只给「运行中」用，绿色只给「完成/通过」，红色只给「失败/危险」。一屏最多出现两个语义色。
