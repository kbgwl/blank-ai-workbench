# v0.11.0：让 Super Agent 真的会醒

> 一句话：以前它「听得懂、会动手、能在群里被叫到」，但**自己到点不会动、盯着东西不会醒**。
> 这版补的是「醒」这件事，以及补之前的两次误判纠正。

## 一、先纠正两个我自己报错的结论

在动手之前我说过三件「真缺」，其中两件是错的。错因是同一个：`grep ... | head -12`
把输出截断了，我拿截断后的结果下了结论。

| 我当时说 | 实际 |
| --- | --- |
| 「全仓没有一处创建 `AgentRun`」 | `services/agent/queue.py:34` 就有。租约、崩溃恢复、跨进程恢复都有测试覆盖（`test_run_lease_v102` / `test_worker_recovery_v152` / `test_crash_resume_cross_process_v142`，25 例） |
| 「没有跨会话记忆」 | `services/memory.py` 有完整 `MemoryStore`（四类记忆、去重、预算上限、原子写），且**已接进主链路**：`runtime.py:897` → `context_curator.curate()` → `memory.search()`，还发 `context.curated` 事件 |

这两件没有改代码。写在最前面，是因为「照着错误清单去修」比不修更糟。

## 二、真正断掉的三处

三处的病象完全一样：**登记成功、永远不醒**。而且都在同一条链路上，只是断在不同的位置。

### 1. 定时：写死了 `fire_at=None`

`_defer_if_needed` 登记触发器时 `fire_at=None`，而 `triggers.due()` 只捞
`fire_at <= now` 的行。于是「今晚 9 点提醒我」会认真登记一条 `pending`，
然后在监控页上永远显示「等一个不会到来的事件」。

修法是新增 `services/agent/schedule.py`（纯函数，15 例单测）：

- 认「今晚 8 点 / 明天上午 9 点 / 下午 3 点 / 8 点半 / 30 分钟后 / 2 小时后 /
  每天 8 点 / 每周一 9 点」；
- **按本地时区理解，再转 UTC 存**。反过来做会整体偏 8 小时——监控页上踩过一次；
- **宁可返回 `None` 也不猜**：猜错时间的代价是半夜跑任务、凌晨发提醒，用户看不见原因；
- 说了「今天下午 3 点」而现在 4 点 → 顺延到明天并标 `shifted`，界面能说「你说的时间已过」；
- 只说「9 点」→ 取最近的未来，这不算顺延。

重复任务不是「一条记录反复放行」：跑完 `mark_fired`，再用带时间戳的 `dedupe_key`
登记下一条，窗口给到点后一周（默认 24 小时对「每周」必然过期）。

**定时意图本身也曾判不出来**：`_SCHEDULE` 只认「定时/每天/到点」这几个词，
「30 分钟后提醒我」进不了这条路，会按普通任务当场跑掉。补的是
「时间表达 + 提醒动词」这条并列条件，时间解析与意图判定共用同一个解析器——
两条口径分叉，就会出现「判定说是定时、登记时解析不出时间」。

### 2. 盯着：`workspace_changed` 没有生产者

`grep` 全仓，`workspace_changed` 这个事件类型没有任何一处 `ingest`。所以
「盯着 X，一有变化告诉我」也是永久等待。

新增 `services/agent/watch_scan.py`，挂进 `supervise_once` 的同一拍巡检：

- 判据是 `mtime > watch_since`（登记时刻），不是「全量指纹对比」。指纹要先建基线，
  而基线只能在登记之后建——建之前的变化会被吸收掉，正好漏掉「我刚一交代就改的那一下」；
- 跳过 `node_modules` / `.git` / `dist` 等依赖与产物目录：一次 `npm install`
  能造上万条 mtime，真改动会被淹掉；
- 扫不动（目录不存在、权限不足）当「没变化」，一条盯不上的监控不该带走整轮巡检；
- 命中后把 `changed` 文件列表写进 payload，放行时自己起跑，并把「盯着」的存活窗口放到 7 天。

### 3. 到点了，但没人执行

`release_due_triggers` 调 `release_one` 时用默认 `start_runner=False`，只入队。
桌面形态没有独立 worker 进程，`recover_pending_runs` 又只在启动时扫一次——
于是定时到点后那条 run 会**永远停在 `queued`**：界面一直转圈，实际没人动。

修法是把「要不要自己起跑」的决定权交给调用方：

- `run_once`（独立 worker 进程）→ `start_runner=False`，它下一行就自己认领；
  这里再起一个就是两个执行者抢同一条 run。
- `supervise_once`（桌面形态）→ 按 `BLANK_INPROCESS_RUNNER` 判断，默认自己起跑。

执行路径仍然只有 `launch_task` 一条，只是不再依赖外部轮询。

### 4. 前三条都通了，却被一个默认关闭的开关挡住

`background_execution` 是 BETA、默认 `False`，而它当时挡着 `_defer_if_needed` 与
`release_due_triggers`。也就是说：客户装好新版，「9 点提醒我」会**当场跑掉**，
「盯着这个文件」会当场执行一次——时间与变化都被忽略，而且没有任何地方告诉他。

这条 flag 的语义是「**后台自主**发起」（Agent 自己决定开一轮修复、自己接着跑），
而定时/盯着是人明确下的指令。拿它去挡用户的话，和 v0.10.3 那次「IM 入站不受它管」
是同一个判断，只是这次漏了这两条路径。

所以把定时/监控从 flag 里摘出来（flag 仍然管自主发起），并把 summary 改清楚。
连带前端两处文案也改：监控页不再显示「后台执行未开启」，消息通道那栏不再暗示
「关着就收不到」。


## 三、自动更新：从「只检查」接到「下载 + 校验 + 一键装」

之前 `main.cjs` 里写着「不下载、不安装、不接 electron-updater」，且有单测钉住
`install` 恒为 false。现在：

1. `decideUpdate` 校验全过后 `install: true`；
2. `downloadUpdate` 把包下到临时目录，**拿真字节算 sha256**；
3. `planInstall`（纯函数）用实际摘要再核一遍——元数据说 `sha256=X` 是「应该是多少」，
   只有算一遍手上这个文件才知道「实际是多少」。不匹配就丢弃并标 `unavailable`；
4. 托盘那一行在下载并验过之后才变成**可点**的「已下载，点此安装」；
5. `applyUpdate` 装之前**再算一次**摘要（下载到安装之间文件可能变），然后 `spawn` 安装器 `/S`。

三道保守：下载不装（静默替换客户正在用的程序，出问题没有回退入口）、装前重算、
默认不碰网络（必须显式配 `BLANK_UPDATE_FEED_URL`）。

## 五、真机验收（安装版 0.11.0）

在装好的 0.11.0 上，**后台自主开关保持默认关闭**，发一句「40秒后提醒我检查一下部署」：

| 时刻 | 事实 |
| --- | --- |
| 发起 | `intent=schedule`、任务停在 `draft`（没有当场跑） |
| 登记 | `fire_at=06:20:41`（发起于 06:20:01，正好 40 秒后）、`never_fires=false`、`waiting_for=到点 … 自动执行` |
| 到点 | t+45s 状态转 `running`（30 秒一拍的巡检，晚几秒是正常的） |
| 结束 | t+140s `succeeded` |

这条跑通同时证明了四件事：时间解析、flag 解绑、到点扫描、桌面形态自己起跑。

再验「盯着」：发一句「盯着工作区的 README.md，一有变化就告诉我改了什么」，
任务停在 `draft`、登记成 `intent=watch`、`never_fires=false`；随后在活动工作区
写一个文件，**t+15s 从 `draft` 转 `running`**，之后进了审批门（`waiting_approval`）——
它想动手改东西，按当前权限档位该停下来问。这条同时证明了事件源真的存在。

**验收时抓到一个真 bug**：`watch_once` 每拍现查 `active_workspace`，而验收时项目
有四个工作区、活动的是另一个目录，于是它在盯 F 盘那个，而我在 E 盘改文件——永远不会触发，
界面上还显示得好好的。修法是在**登记时把路径固化**进 payload（`watch_root`），
巡检优先用它；之后用户切换活动目录，也不会让这条盯着悄悄换地方。

**没有验证到的**：到点后不会弹系统通知。任务确实执行了，但结果里那句「提醒已弹出」
是模型自己编的——它没有通知通道可用。这是下一步的事（需要桌面通知权限、去重、
以及尊重免打扰时段），不是这一版能顺带做掉的。

## 六、没验的

- **真实厂商账号的端到端收发**（企业微信/钉钉/飞书）：缺的是客户自己的凭据，不是代码路径。
  假凭据验到「错误码能原样念出来」这一层。
- **真实更新 feed 的完整链路**：本地 http 桩跑通了「检查 → 下载 → 校验 → 可安装」，
  但没对着真实发布通道跑过；`applyUpdate` 真的拉起安装器这一步也没在本机点过。
- **钉钉 Stream 真连网关**：只做过帧格式单测。
- **本机 GUI 里的托盘菜单观感**：`main-wiring` 用的是假 Electron，逻辑跑通但没截图。
