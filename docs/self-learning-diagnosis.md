## 二、实测出来的四个窟窿

### 窟窿 1：79% 是垃圾

`kbgai-f1a6db42.md` 共 **57 条**，其中 **45 条是冒烟测试的流水账**：

```
## 2026-11-18 · 冒烟：调工具 · 任务 d93911c6
- 结果：结论 - 顶层共 30 项，前 5 个都是目录：`.acceptance`、`.blank_backups`…
```

同一条事实（"顶层有 31 项、前 5 个是目录"）在不同任务里重复了 **13 次**。

**根因**：`_consolidate()` 无条件写——只要任务成功就写，不看这次有没有值得跨任务记住的东西。
冒烟测试的任务也是"成功"的。

### 窟窿 2：自相矛盾，且旧结论不会失效

```
- 结果：…这台机器是 Windows cmd.exe，没有 `rm` 命令。
- 结果：…这台机器的 shell 里有 `rm`，旧结论已纠正。
```

前者 2 条、后者 3 条，**并存**。`memory_search` 检索"rm"会同时返回它们，
模型拿到的是一条自相矛盾的记忆——比没有记忆更坏。

**根因**：只有"追加"，没有"覆盖"和"失效"。记忆是 append-only 的流水账。

### 窟窿 3：只写不读

记忆写入后，**执行时不会自动进上下文**。`instructions.py` 的指令分层是
`system / user / project(AGENTS.md) / harness(.blank/harness) / task`——**没有 memory 层**。

模型只有在自己想起来调 `memory_search` 时才读得到。而它不知道"这次该查什么"，
因为**它不知道自己正在踩一个踩过的坑**。

这就是"自学习没闭环"最精确的形态：写了 7,584 行（全目录），一条也没自动回来。

### 窟窿 4：失败经验不回流

`_consolidate()` 挂在 `if status == "succeeded"` 分支里。失败的任务——正是最有教训的那些——
一条记忆都不写。

真机例子：`npm test` 超时这个坑，今天在不同的任务里踩了三次（3D 工厂 / deepseek 轮 /
讯飞轮），每次都是从头再踩。真正记住它的是我后来手写的"慢命令记忆"
（`test-command-history.json`）——**一个机制，而不是一条记忆**。

这说明：**光有记忆不够，得有"把教训变成机制"的路径。**

## 三、由此推出的设计约束

1. **要有准入**：不是所有成功任务都值得记。判据得是"跨任务仍有价值"，而不是"这次成功了"。
2. **要能失效**：同一主题的新认识必须能覆盖旧的，否则记忆会自己和自己打架。
3. **要自动注入**：不能指望模型想起来查。任务开始时按目标检索相关记忆，进提示词。
4. **失败也要记**：而且失败记忆的价值通常高于成功记忆。
5. **记忆不是终点**：真正的教训应该沉淀成**机制**（一条规则 / 一个断路器 / 一个默认值），
   而不只是一段文字。`test-command-history.json` 比任何"记得别跑 npm test"的文字都有效。

## 四、待验证的问题（等调研回来对照）

- 准入判据怎么定才不误杀？（"这次改了文件"够不够？）
- 去重用什么做键？（事实指纹 / 主题标签 / 语义相似）
- 自动注入的检索：关键词够不够，还是要语义？注入几条、占多少字符预算？
- 怎么知道注入的记忆**真的有用**？（要有反馈信号，否则又是"写了不知道有没有用"）
- 怎么防"agent 写错经验 → 照着做 → 更错"的自我强化循环？
