# 「成果比别人好」怎么算

「好」如果只是感觉，就没法验收，也没法回退。这份文档把它拆成五个**机器判定**的分项，
同一批任务、同一套判分，跑我们自己和对标产品，出同一张表。

判分脚本：`evals/compare.mjs`。同一批题目来自 `evals/task-samples.json`（32 个任务，
每家有独立的 fixture 工作区，每次跑前重建）。

## 五个分项

| 分项 | 权重 | 怎么判 | 为什么是它 |
|---|---|---|---|
| 正确性 | 45% | 任务自带的 `verify` 命令（`pytest -q` / `node --test`）在我们自己手里跑，全绿才算 | 它自己说「已修复」不算数；测试是唯一不靠嘴的证据 |
| 命中率 | 20% | `expect_files` 里要求的文件，实际被改动的比例 | 改了不相干的地方、或者根本没动到该动的文件，都算没完成 |
| 最小改动 | 15% | 期望之外的文件改动数：0 个满分，1 个 0.6，2 个 0.3，3 个以上 0 | 顺手重构是最常见的「看起来做了很多、实际更难维护」 |
| 自证 | 10% | 它自己有没有跑过验证命令 | 「改了就不管」和「改完自己验一遍」是两种产品 |
| 成本 | 10% | 同一题里 token 最少的拿满分，其余按比例 | 同一件事花 10 倍钱，不能算一样好 |

综合分 = 45%×正确 + 20%×命中 + 15%×最小 + 10%×自证 + 10%×成本（满分 100）。

三个关键设计：

1. **验证命令由判分器执行，不由 agent 执行。** agent 说「测试全绿」没有任何分量。
2. **工作区逐字节对比**，不用 `git diff`：fixture 是从零铺出来的，没有 git 历史。
3. **成本只在同一题内归一**。跨题比 token 没意义——一个是「加一个函数」，一个是「修一个构建」。

## 怎么跑

```bash
# 三家一起跑三个任务（需要本机有 claude / codex CLI）
node evals/compare.mjs --only T01,T02,T03 --agents ours,claude,codex

# 只跑我们和对标，指定一个干净的后端（推荐：独立库，不污染日常使用记录）
node evals/compare.mjs --api http://127.0.0.1:8060/api/v1 --only T01,T02,T03 --agents ours,claude

# 看它到底判了什么
cat evals/results/compare-*.json
```

每家跑之前都会 `rm -rf` 并重建工作区；`--keep` 可保留现场，`--cleanup` 会删掉
评测过程中建的项目。

我们这边需要后端在跑（`ours` 走 HTTP API，创建项目→工作区→任务→运行→读 evidence）。
独立后端的起法见 `docs/COST.md` 的复核段落：复制一份 `blank.db` 与 `.blank_secret.key`，
用 `BLANK_DATABASE_URL` 指过去，端口 8060。

## 第一次实测（2026-10-21，本机）

`node evals/compare.mjs --only T01,T02,T03 --agents ours,claude`，两家各自从 fixture 重建工作区：

| 任务 | 空白格 | Claude Code |
|---|---|---|
| T01 给文本工具加 `truncate` + 测试 | **100 分** · 52K token · 10 轮 · 24s · 测试通过 | 35.6 分 · 847K token · 23 轮 · 128s · 测试**未**通过 |
| T02 `parse_minutes` 支持 `1:30` | **100 分** · 66K token · 11 轮 · 25s · 通过 | 29.9 分 · 722K token · 20 轮 · 144s · 测试**未**通过 |
| T03 修 `index.js` 导出错误 | 35 分 · 31K token · 7 轮 · 19s · 0 文件改动 | 25.6 分 · 511K token · 15 轮 · 148s · 0 文件改动 |

能这样说：**这三件日常小活上，分数更高、token 少一个数量级、耗时短 5 倍**；
T01/T02 我们的 pytest 全绿，它两次没通过。

不能这样说：

- 样本只有 3 个，**不足以对外宣称「全面超过」**。要下这个结论至少得把 32 个样例跑满。
- 模型不同（DeepSeek vs glm-4.5-flash），所以这不完全是产品对产品的比较。
  换成同一个模型重跑，才是产品级结论。
- T03 的 fixture 其实早就修好了（基线 3 个测试全绿），两边都没动文件、都没得分。
  这条同时证明判分器不奖励"什么都不做"：**验证通过但一行没改，正确性记 0**。

## 判分器自己的坑（踩过就别再踩）

- **基线本来就绿**：多数样例要求的是"新增能力 + 新增测试"，既有测试一开始就是绿的。
  所以不能用"基线失败"当有效性门槛，改成"验证通过 **且** 确实改过文件"才给正确性分。
- **`.blank_backups` 是应用自己的备份目录**（下划线，不是横线）。第一版把它算进
  "改动文件"，导致每次正经改动都被扣「最小改动」分——评测工具冤枉被测产品是最难查的错。
- **Windows 上目录清理会 EPERM**：agent 进程刚退出时句柄还没放开，`rm -rf` 直接抛错
  把整轮评测带崩。清理必须容错重试，不能让它毁掉已经跑出来的数据。
- **竞品 CLI 要绝对路径**：`E:\env\bin` 在 git-bash 的 PATH 里，但 cmd 不认 POSIX 路径，
  `spawn(name)` 直接找不到。

## 已知偏差（读分前先读这一段）

- **模型不是同一个。** 我们默认走用户在设置里配的供应商（这台机器是 DeepSeek），
  对标的 Claude Code 走它自己的网关（这台机器是 bigmodel 的 glm-4.5-flash）。
  分数里既有产品差异也有模型差异，别把两者混为一谈。输出末尾会打印每家实际用的模型名。
- **自证是启发式。** 我们的实现读工具调用明细（`run_tests` / `run_shell` 的命令），
  判得很准；Claude 的 `--output-format json` 不含工具明细，只能从它自己的报告文本里
  找验证命令，因此**可能低估**。命中率与正确性两项不受影响。
- **codex 当前在这台机器上不可用**：`codex` 配置的模型在 OpenRouter 免费层已下线
  （`models/nex-agi/nex-n2.5-pro:free` 返回 404），评测会把它标成 `unavailable`
  而不是算 0 分。换模型后重跑即可。
- **任务集偏小偏轻。** 32 个样例都是小规模改造（加函数、修导出、补嵌套路径），
  代表「日常小活」，不代表长周期大型重构。

## 我们要在哪些维度上真的超过它

按上面的权重，能靠产品设计拿到的分集中在三处，这三处也是当前的改进重点：

1. **自证（10%）**：我们的验证门会真的跑测试并把结果写进交付，对标产品常常要人催。
2. **最小改动（15%）**：验收条件写入任务，交付前对「改了哪些文件」有审查步骤。
3. **成本（10%）**：见 `docs/COST.md` 的四条减 token 机制——工具输出分级、相同输出折叠、
   补丁结果不回吐 diff、shell 方言一次说清。

不靠权重也能看见的差异，属于质的部分，这里刻意不打分（容易被漂亮的文字骗分）：
交付里有没有说清「没做什么」、失败时给的是不是可修复的信息、能不能从事件流把过程溯源出来。
