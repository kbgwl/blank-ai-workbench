# B8 前端交付闸门：从“拦住”到“能自修”（2026-11-22）

> 背景：B7 真实任务已经写出可运行的工作台，但前端改动后没跑 `browser_check`；
> 1.5M token 预算在 UI 修复前耗尽，任务被判 failed。B8 只修这条交付链，
> 不扩功能、不改 UI 布局。

## 一、做了什么

1. **预算外保留一次 UI 修复**
   - `AgentState` 增加 `ui_repair_rounds`；
   - UI 闸门失败时累加；
   - `route_after_validation` 在 `budget_exhausted` 时，仅对
     `validation.command=ui_check` 且 `ui_repair_rounds<=1` 放行一次
     `execute_action`；
   - 第二次 UI 失败仍按预算收尾，不能无限续杯；
   - 过渡解释新增 `ui_repair_reserve`。
2. **保留修复回合允许调用工具**
   - 普通预算耗尽提示是“不要再调用任何工具”；
   - 这会把保留修复变成纯总结。现在这一回合改为：
     “只允许 browser_check + 必要 run_shell + 修复，不探索、不做新功能，
     修完立即收尾。”
   - `budget.exceeded` 事件记录 `reserved_ui_repair`。
3. **browser_check 使用说明补坑**
   - `expect` 只放打开时就存在的元素；
   - 聊天消息/点击后才出现的列表放进 `steps` 的 `assert`，不要一打开就断言 0 个；
   - 修复提示同步写清这一点。
4. **生成页面自带 favicon**
   - 前端系统规则加入 `<link rel="icon" href="data:,">` 的底线；
   - 避免 `/favicon.ico` 404 被零错误闸门算成控制台错误。
5. **测试**
   - UI 闸门：预算耗尽保留一次、第二次不再保留、非 UI 失败不保留；
   - 过渡解释 `ui_repair_reserve`；
   - 系统提示哈希同步。

## 二、真机验证

### 2.1 B7 全量复跑（最终提示词之前）

- 任务 `cd9e077b-...`：failed，29 步 / 34 调用 / **1,692,745 token**；
- 这次**保留了 UI 修复**：`ui_repair_reserve` 生效；
- 模型调用了 **6 次 browser_check**，不再“完全不验”；
- 但它自己的断言写错了：一打开就断言 `#chatLog .msg` 有 1 条，实际初始为 0；
  后续几轮又用错的时间/选择器，最后仍没有一张“断言 + 动作都通过”的回执。
- 结论：预算保留生效；剩下的是 **browser_check 自检写法**问题。

### 2.2 最终提示词下从头复跑（仍失败）

任务 `31ff9212-...`：

- **failed**，28 步 / 33 调用 / **1,669,607 token**；
- `ui_repair_reserve` 再次生效，`budget.exceeded` 记了 `reserved_ui_repair=true`；
- 但模型在这一回合**一次 browser_check 都没调用**（工具序列里没有），
  第二轮仍是 `ui.check_failed`；
- 结论：预算机制修好了，但“给模型一句提示它就会自检”不成立。还需要
  确定性的工具约束/自动探测，不能只靠提示词。

### 2.3 同一工作区的 UI 自检任务（成功，但不是保留路径）

在同一个已生成工作区上，新开一个小任务，只做 UI 自检、不改功能。
**注意：这个任务没有耗尽预算，且任务书已明确写出 expect/steps 的顺序；
它验证的是“页面本身可用、browser_check 能写对”，不是“预算耗尽后的最终
保留提示已端到端生效”。**

- 任务 `1999e815-...`：**succeeded**
- **19 步 / 21 次调用 / 844,374 token**
- 最后一轮 browser_check：**9 项 expect、6 个动作全部通过**，控制台和失败请求均为 0
- 验收 3/3：
  - 最新代码上 browser_check 通过
  - 控制台零错误、零失败请求
  - 快捷巡检与发送消息都有回执
- 模型自己的结论：“首轮未通过是因为断言在回执前执行，并非页面缺陷。”
- 同一页面用我们独立探针复核：**10/10 动作通过，控制台 0 错误**。

这说明：**只要给对 browser_check 的断言顺序，页面和检查工具本身是能过的**。
但最终提示词下的完整 B7 仍没有调用 browser_check，因此不能把 2.3 的成功
等同于“保留修复路径已经可靠”。

## 四、结论

1. B8 把“预算一尽就直接失败”改成“保留一次 UI 修复”，且这一次真的允许调用工具；
2. 2.1 复跑里模型确实调用了 browser_check，说明闸门不再只是拦；但 2.2 的最终
   复跑里模型一次都没调用，说明“只靠提示”不稳定；
3. 真正的失败点从“没预算”变成了“模型不服从自检提示 + 不会写断言”；
   2.3 用明确任务书证明页面和 browser_check 都能通过，但该任务预算未耗尽；
4. 下一步需要**确定性约束**：保留修复回合强制 browser_check，或验证节点自动
   做轻量页面探测；不能继续只加提示词。

## 五、边界

- 只验证了 DeepSeek；没有 Claude/Codex 同题对照。
- 2.3 的小任务**预算未耗尽**，且任务书明确写了检查顺序；它不能证明保留
  修复提示已经可靠。最终保留路径已经从头的端到端复跑并失败（2.2）。
- UI 自检任务 844K token 仍然偏贵；B8 没解决大任务成本，只解决“差一步”的交付。
- 保留修复只有一次；第二次 UI 失败仍会按预算收尾，这是有意的。
- favicon 规则是提示词底线，不是硬编码生成；仍需真实 browser_check 验证。
- 生成 app 与 evidence 保留在 `_bench_workspaces/b7-shopbench-ours`、
  `data/b8-ui-repair-evidence.json`、`data/b8-evidence.json`、
  `data/b8-final-evidence.json`。
