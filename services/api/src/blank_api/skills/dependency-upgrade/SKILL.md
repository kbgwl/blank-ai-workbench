# 依赖升级

## 升之前

1. 记下**当前版本**和**目标版本**，看中间跨了几个大版本。
2. 查 breaking changes：优先读官方 CHANGELOG / Migration Guide；仓库里没有就问一次搜索，
   把「哪几条会影响本项目」列出来（不要只贴一段官方原文）。
3. 判断影响面：`search_code` 找出所有调用这个库的地方——只列真实调用点。

## 升的时候

- **一次只升一个包**（同一家族可以一起升，比如 `@types/*` 跟主包）。
- 锁文件一起提交；不要手动改锁文件内容。
- 大版本跨越时，先升到中间最后一个次要版本，再升上去：出问题时能定位是哪一跳坏的。

## 升完

- 跑测试 + 类型检查，记退出码与数量。
- 手工核对一遍 API 变动点（类型系统不报错不代表语义没变）。
- 如果失败，**回退而不是硬改业务代码**；确实必须改，就单独作为一次改动，说清为什么。

## 报告

```
<包> <旧版本> → <新版本>
- 破坏性变更：<列条目，或"无">
- 影响到的调用点：<文件:行>
- 验证：<命令> → EXIT=0，N passed
```
