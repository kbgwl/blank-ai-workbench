# 代码审查

## 一、先取范围（不取范围就审 = 瞎猜）

1. `git status` 看有哪些改动，`git diff --stat` 看规模。
2. 只看**本次改动**。改动超过 5 个文件时先按目录分组，逐组看，别一次性吞完。
3. 改了函数签名 / 返回值结构，必须用 `search_code` 把所有调用点找出来，向外扩一层再判断。

## 二、检查顺序（前三条命中就是阻断）

1. **会出错**：空值、越界、并发、失败分支；异常被 `except: pass` 吞掉；返回值没检查。
2. **会坏数据**：写库前没有校验；迁移不能回滚；删除/覆盖没有二次确认。
3. **安全**：外部输入直接进 SQL / shell / 文件路径；密钥或令牌进日志；鉴权只做在前端。
4. **契约**：接口字段删改是否同步了前端与文档；老数据能不能继续读。
5. **可验证**：有没有对应的验证手段。没有就如实写「未验证」，不要写「应该没问题」。

## 三、输出格式

- 分三档：`阻断`（必须改）/ `建议`（应该改）/ `可选`（风格与命名）。
- 每条一行结论 + 证据：`路径:行` → 「现在会怎样」→「改成什么」。
- 每条都必须能落到具体行。给不出位置的，降级成「整体观察」，不要冒充具体问题。
- 最后一句给判断：能合 / 改完阻断项再合。

## 四、禁止

- 不为凑数编问题（「建议加注释」这种没有信息量的不进结论）。
- 不重写作者的风格；只有它带来真实风险时才提。
